# 主控串口崩溃与命令队列扩容 — 重构需求 v1.0

> 文档目的：把 `std::bad_alloc` 崩溃 + 队列/缓冲区扩容的方案固化下来，作为后续编码依据。
> 启动时机：本重构排在 **MoveJ 速度与同步抵达重构** 同步进行（共享 ASCII 协议层）。

---

## 1. 背景与现状

### 1.1 用户报告的一个实测问题（2026-08-31）

| # | 现象 | 影响 |
|---|------|------|
| A | 连续发送 5 条 `#ACC_J` 后立刻发 MoveJ，主控崩溃（`std::bad_alloc`），Python 报 Write timeout | 固件失去响应，必须重启 |

### 1.2 复现路径（来自用户日志）

```
#ACC_J 1 400
#ACC_J 2 400
#ACC_J 3 400
#ACC_J 4 400
#ACC_J 5 400        ← 5 条连发
>0.0,-75.0,180.0,0.0,0.0,0.0,100.0,50.0    ← 紧接着 MoveJ
```

崩溃发生在 MoveJ 入队/解析期间，固件打印 `terminate called after throwing an instance of 'std::bad_alloc'` 后卡死。

---

## 2. 根因（已诊断）

崩溃有 **两个叠加因素**，单修一个都不够：

### 2.1 因素 ① — `std::string` 频繁堆分配（崩溃根因）

`CommandHandler` 的整个生命周期都依赖 `std::string`：

| 位置 | 当前类型 | 堆分配点 |
|---|---|---|
| `Push(const std::string&)` | 入参 `std::string` | 调用方可能触发 SSO 阈值外拷贝 |
| `Pop(uint32_t)` 返回值 | `std::string` | 返回 `std::string{strBuffer}`，命令 >15 字符必走 `new/delete` |
| `ParseCommand(const std::string&)` | 入参 `std::string` | 拷贝入参 |
| `main.cpp:118-119` | `ParseCommand(Pop())` | 每轮循环至少 2 次构造+析构 |
| `ascii_protocol.cpp` 协议层 | `std::string s(_cmd)` | 每条指令入口都构造一次 |

**关键阈值**：GCC ARM 13.2 默认 SSO 阈值约 15 字符。MoveJ 命令实际长度：
```
>0.0,-75.0,180.0,0.0,0.0,0.0,100.0,50.0    ← 38 字符
$100.0,200.0,300.0,400.0,500.0,600.0,700.0  ← 41 字符
```
**全部超过 SSO 阈值 → 每次都走 `new/delete`**。

STM32 堆（`HEAP_SIZE = 0x1800 = 6144 字节`）被高频小块申请打碎，碎片化达到临界点后 `new` 抛 `std::bad_alloc`，固件进入 C++ terminate → 看门狗超时 → Python 报 Write timeout。

### 2.2 因素 ② — 队列/缓冲区偏小（容量瓶颈）

| 位置 | 当前值 | 用途 |
|---|---|---|
| `osMessageQueueNew(16, 64)` | 16 条 × 64 字节 | 存命令队列 |
| `char strBuffer[64]` | 64 字节 | Pop 内部读取缓冲 |
| `Respond` 内 `response[64]` | 64 字节 | 响应栈缓冲 |

最长响应（已实测）：
```
ok SET MOTOR [8] ACCELERATION [%.2f] r/s^2 (夹爪)   ← 50+ 字符
ok GETJACC ...                                       ← 30 字符
```

虽然 64 字节未溢出，但当 16 条队列瞬间占满（如 ServoJ 1kHz 力矩透传），新指令被丢弃，调用方无从感知。**扩容到 128 字节给未来 2× 余量**。

---

## 3. 重构目标

1. **消除所有 `std::string` 临时对象** —— 命令路径全程走 `const char*` + 内部栈缓冲
2. **队列容量翻倍** —— 16→32 条，64→128 字节
3. **响应缓冲区翻倍** —— `response[64]` → `response[128]`
4. **接口兼容性** —— `Push(_cmd)` 调用方无需改动（`_cmd` 本来就是 `const char*`）

---

## 4. 实施方案 = 方案 C（A+B 组合）

| 方案 | 内容 | 状态 |
|---|---|---|
| A — 仅扩容队列/缓冲区 | 治标不治本，崩溃仍会复现 | ❌ 不采用 |
| B — 仅去堆化（接口改 `const char*`） | 治本但队列容量仍是瓶颈 | ❌ 不采用 |
| **C — 扩容 + 去堆化** | 治标 + 治本，双保险 | ✅ **采用** |

### 5.3 文件 `firmware/ref_core_f405/Robot/instances/dummy_robot.cpp`

**改动 3.1** — 第 711-720 行 `Push` 实现

```cpp
// 旧
uint32_t DummyRobot::CommandHandler::Push(const std::string &_cmd)
{
    char buf[64] = {0};
    strncpy(buf, _cmd.c_str(), sizeof(buf) - 1);
    osStatus_t status = osMessageQueuePut(commandFifo, buf, 0U, 0U);
    if (status == osOK)
        return osMessageQueueGetSpace(commandFifo);
    return 0xFF;
}
// 新
uint32_t DummyRobot::CommandHandler::Push(const char *_cmd)
{
    char buf[128] = {0};
    strncpy(buf, _cmd, sizeof(buf) - 1);
    osStatus_t status = osMessageQueuePut(commandFifo, buf, 0U, 0U);
    if (status == osOK)
        return osMessageQueueGetSpace(commandFifo);
    return 0xFF;
}
```

**改动 3.2** — 第 741-745 行 `Pop` 实现

```cpp
// 旧
std::string DummyRobot::CommandHandler::Pop(uint32_t timeout)
{
    osStatus_t status = osMessageQueueGet(commandFifo, strBuffer, nullptr, timeout);
    return std::string{strBuffer};
}
// 新
const char* DummyRobot::CommandHandler::Pop(uint32_t timeout)
{
    osStatus_t status = osMessageQueueGet(commandFifo, strBuffer, nullptr, timeout);
    if (status == osOK)
        return strBuffer;
    return nullptr;
}
```

**改动 3.3** — 第 759 行 `ParseCommand` 签名同步

```cpp
// 旧
uint32_t DummyRobot::CommandHandler::ParseCommand(const std::string &_cmd)
// 新
uint32_t DummyRobot::CommandHandler::ParseCommand(const char *_cmd)
```

**改动 3.4** — `ParseCommand` 内部实现

原代码中所有 `_cmd.c_str()` / `_cmd.length()` / `_cmd.find()` 等 `std::string` 接口需要替换为 C 字符串接口：
- `_cmd.c_str()` → 直接用 `_cmd`（已经是 `const char*`）
- `_cmd.length()` → `strlen(_cmd)`
- `_cmd[N]` → 兼容（下标访问 C 字符串仍合法）
- `_cmd.find("...")` → `strstr(_cmd, "...")` 返回 `nullptr` 表示未找到
- `_cmd == "xxx"` → `strcmp(_cmd, "xxx") == 0`

⚠️ `ParseCommand` 函数体较大（涉及 `MoveJ`/`MoveL`/`ServoJ`/`SetJointCurrents` 等子函数），需要逐段替换。

### 5.4 文件 `firmware/ref_core_f405/UserApp/main.cpp`

**改动 4.1** — 第 118-120 行消费者循环

```cpp
// 旧

// 新

if (_cmd != nullptr)

```

### 5.5 文件 `firmware/ref_core_f405/UserApp/protocols/ascii_protocol.cpp`

**改动 5.1** — 第 688 行 / 702 行 / 1329 行 `Push` 调用

✅ **无需改动** —— `_cmd` 本身就是 `const char*`，与新签名完全兼容。

## 6. RAM 资源消耗估算

| 项目 | 旧 (字节) | 新 (字节) | 增量 |
|---|---:|---:|---:|
| 消息队列缓冲 | 16 × 64 = 1024 | 32 × 128 = 4096 | +3072 |
| `strBuffer` | 64 | 128 | +64 |
| `Respond` 栈缓冲 | 64 | 128 | +64 |
| **合计** | **1152** | **4288** | **+3200** |

STM32F405RG 总 RAM = 128 KB（`0x20000`），新增 3.2 KB 占比 **2.5%**。FreeRTOS 堆 (`HEAP_SIZE = 0x1800 = 6144` 字节) 保持不变。

---

## 7. 收益 vs 风险

### 7.1 收益

| 项 | 效果 |
|---|---|
| `std::bad_alloc` 崩溃 | **根除**（命令路径无 `new/delete`） |
| 队列容量 | ×2 倍（可缓冲更多高频指令） |
| 命令长度上限 | 63 → 127 字符（当前最长 50 字符，留 2× 余量） |
| 响应长度上限 | 63 → 127 字符（防未来截断） |
| 高频入队（如 ServoJ 1kHz 力矩） | 队列满前不会丢弃指令 |

### 7.2 风险

| 风险 | 缓解 |
|---|---|
| 接口签名改动需同步 `main.cpp` | 已规划在改动 4.1 |
| `ParseCommand` 内部需要全面改写 `std::string` → C 接口 | 改动 3.4，需仔细替换 |
| 调用方 `Push(_cmd)` 兼容 `const char*` | 已确认兼容，无需改 ascii_protocol.cpp |
| RAM 增加 3.2 KB | F405 128KB 占比 2.5%，安全 |

### 7.3 回滚方案

所有改动可一次性 revert（git 暂未提交当前 stash）。
