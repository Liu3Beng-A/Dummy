## 4. 实测根因诊断：**`SetEnable(true)` 阻塞 + 优先级倒挂**

### 4.1 调用链追踪

```
!START (ASCII 线程, osPriorityNormal)
  └─ dummy.SetEnable(true)                     // dummy_robot.cpp:611
       ├─ SetRGBMode(rgbStateEnable)           // 只改 mode 变量，瞬时
       ├─ for i=1..6:
       │   motorJ[i]->SetEnable(true)          // ctrl_step.cpp:22
       │     ├─ state = FINISH                 // ★ 主控侧同步置位
       │     └─ CanSendMessage(...)            // interface_can.cpp:194
       │         ├─ osSemaphoreAcquire(sem_can1_tx, osWaitForever)
       │         └─ HAL_CAN_AddTxMessage(...)
       ├─ motorJ[0]->SetEnable(true)           // 地轨
       └─ hand->SetEnable(true)                // 夹爪
  └─ Respond("ok")                             // 写 UART4 + USB
```

### 4.2 系统参数

| 参数 | 值 | 来源 |
|---|---|---|
| `sem_can1_tx` 计数 | **1**（`osSemaphoreNew(1, 1, ...)`）| `freertos.c:346` |
| CAN1 TX mailbox 数量 | **3** | STM32F405 硬件 |
| `CanSendMessage` 超时 | **`osWaitForever`** | `interface_can.cpp:194` |
| `ControlLoopFixUpdateTask` 优先级 | `osPriorityRealtime` | `main.cpp:302` |
| `ControlLoopUpdateTask` 优先级 | `osPriorityNormal` | `main.cpp:311` |
| `OledTask` 优先级 | `osPriorityNormal` | `main.cpp:320` |
| `RGBTask` 优先级 | `osPriorityNormal` | `main.cpp:328` |
| CAN TX 完成中断 | **`CAN_IT_TX_MAILBOX_EMPTY`**（非 `_COMPLETE`）| `interface_can.cpp:75` |

### 4.3 真凶 #1：**`SetEnable(true)` 内部同步发 8 次 0x01**

- 一次性循环 7 个电机 + 1 个夹爪 = 8 次 `osWaitForever` 串行等待 sem_can1_tx
- 最坏情况：8 × 30ms（单帧 CAN 发送 + 回包延迟）= 240ms ASCII 线程阻塞
- 此时所有 ASCII 解析挂起，**RGB 任务虽然独立但与 ASCII 任务同时被实时环抢占**

### 4.4 真凶 #2：**优先级倒挂**

- `ControlLoopFixUpdateTask` 是 `osPriorityRealtime`（最高），5kHz 由 TIM7 中断驱动
- 每 100 个 tick（50Hz）调用 `dummy.MoveJoints()` → 7 次 `motorJ[i]->SetAngleWithMotorRps()` → 7 次 `CanSendMessage()` → 7 次 `osSemaphoreAcquire(sem_can1_tx, osWaitForever)`
- 这是每秒 7 × 50 = 350 次 `osWaitForever`
- **如果任何一次 HAL_CAN_AddTxMessage 返回 BUSY 或 NACK 失败，semaphore 永远不释放**，后续所有发 CAN 的代码全部卡死
- **后果**：
  - ASCII 线程后续 `!START` / `!DISABLE` 路径上的 `CanSendMessage` 全部卡死
  - 实时环后续 `MoveJoints` 卡死 → 但实时环阻塞不会饿死自己（它就这一个 task），而是**阻塞实时环后续执行 → 但实时环总在 ulTaskNotifyTake 里等 TIM7 通知**
  - **更危险**：实时环被卡死 → 但还**会持续占 CPU 在 osWaitForever 上自旋**（FreeRTOS 行为）→ 永久耗尽 CPU 时间 → Normal 优先级的 RGB / OLED / ASCII 全部饿死

### 4.5 真凶 #3：**电机端使能后立刻进入位置控制**

- 电机端 `interface_can.cpp:32` 收到 0x01 后调用：
  - `motor.controller->ResetGoalsToCurrentPosition()`：goalPosition = estPosition
  - `motionPlanner.positionTracker.NewTask(estPosition, estVelocity)`：trackPosition = estPosition
  - `motor.config.motionParams.ratedVelocity = boardConfig.velocityLimit`：恢复速度
- 电机端状态切到 `MODE_COMMAND_POSITION`（如果之前在 MODE_STOP）
- 电机开始 PID 闭环维持当前位置（`CalcDceToOutput(estPosition, 0)`）
- **如果机械臂位置差大、或当前位置不在归零点附近，电机开始移动**
- 移动过程中电机端 v3 堵转检测每 20kHz 检查一次，**触发堵转条件**（电流×40%、低速、大误差）广播 0x5A
- 主控 can_protocol 简化版不处理 0x5A，**但每帧 0x5A 都消耗 CAN 控制器一个接收 ISR**
- 如果多个电机同时进入堵转，CAN 总线被刷爆，0x23 位置查询响应延迟

### 4.6 真凶 #4：`main.cpp:221` `osDelay(20)` 硬节流 OLED

- 旧版 `source code/` 主控没有这个 `osDelay(20)`
- 新版加了这个注释："设置硬休眠 20ms 以削峰屏刷新占时"
- **实测删掉后帧率恢复到 ~50Hz（与旧版一致）**
- 软件 I2C 自然限速，不需要硬延迟

### 4.7 真凶 #5：`UpdateJointAngles()` 4 组轮询策略

- 每 tick 只查一组（2 轴），组 0/1/2/3 轮询
- 调用频率 `updateCounter % 50 == 25`（5kHz / 50 = 100Hz ÷ 4 组 = 每轴 25Hz）
- 每轴刷新率 25Hz，比旧版（全量 5kHz × 7 轴已不可能）的设计更慢
- **改回全量查询可恢复到 50Hz/轴**

## 6. 待定项（等用户决策）

### 6.1 `SetEnable` 方案选择

**问题**：`SetEnable(true)` 一次性发 8 个 CAN 0x01 命令，每个 `osWaitForever` 等 `sem_can1_tx`，最坏阻塞 240ms。

**方案甲（推荐）**：拆分使能请求 + 主循环分批发送
```cpp
void DummyRobot::SetEnable(bool _enable)
{
    isEnabledRequested = _enable;
    // 不立即发 CAN，把 8 个 motor 推进 enablePending[]，由主循环在下次 service 时分批发
    // 主循环示例（每 5kHz tick 内最多发 1 个 motor）：
    //   if (isEnabledRequested && enablePending[i]) {
    //       motorJ[i]->SetEnable(_enable);  // 内部短超时 5ms 等待
    //       enablePending[i] = false;
    //   }
}
```
- ✅ 不阻塞 ASCII 线程
- ✅ 总使能时间 ≈ 8 × 200μs = 1.6ms（在实时环内分批完成）
- ⚠️ 需要在实时环里分批发送逻辑

**方案乙**：保留同步发，但改 `osWaitForever` 为 timeout=100ms
```cpp
osStatus_t CanSendMessage(...) {
    if (...) semaphore_status = osSemaphoreAcquire(sem_can1_tx, 100);
    if (semaphore_status == osOK) HAL_CAN_AddTxMessage(...);
    else { /* 超时丢弃，本次发送失败，重试或报警 */ }
}
```
- ✅ 改动小
- ❌ 100ms × 8 = 800ms 阻塞 ASCII 线程（更糟）
- ❌ 信号量丢失后需要补偿发送

**方案丙**：增加 sem_can1_tx 计数为 3（匹配 TX mailbox 数量）
```cpp
osSemaphoreNew(3, 3, ...);  // 匹配 3 个 mailbox
```
- ✅ 改动最小
- ✅ 立即发 8 个变可缓存 3 个并发
- ⚠️ 仍需重排等待逻辑（HAL_CAN_AddTxMessage 多 mailbox 支持需查 ST 手册）

### 6.2 `jointsStateFlag` 预置策略（修复 #5 时需要决策）

**问题**：电机使能后第一个 0x23 回包前，主控侧的 jointsStateFlag bit 状态不可控。
- 若按 A1 修复（FINISH→|=，非 FINISH→&=），电机使能后第一个回包电机端 `state == STOP`（电机刚收 0x01 还在初始化），按"非 FINISH"分支会清 bit → IsMoving 永真

**方案 A**：电机端 0x01 收完立即发一个 0x23 "已就绪" 包，isFinished=1
- 改动在电机固件接口_can.cpp
- 需要与电机端对齐

**方案 B**：主控 `SetEnable(true)` 后**预置**所有 bit 为 1，等 0x23 回包纠正
```cpp
void SetEnable(true) {
    // 预置：乐观认为电机立即就绪
    jointsStateFlag |= 0b1111110;  // bit 1~6 全部置 1
    // 然后正常发 CAN 0x01
}
```
- ✅ 主控改动，电机端不动
- ⚠️ 如果电机端发回包延迟大，预置期间 IsMoving 会返回 false，但实际电机还没到位

**方案 C**：保留 A1 修复方向不变，但用 isEnabledRequested 标志
```cpp
bool IsMoving() {
    if (isEnabledRequested && !isEnabled) return true;  // 等待首次使能完成
    return jointsStateFlag != 0b1111110;
}
```
- ✅ 改动最小
- ✅ 与 #5 方案甲配合顺滑

## 10. 代码探索验证：关键发现

> 本节记录对固件代码的深度探索，验证文档假设并修正错误描述。

### 10.1 `CanSendMessage` 信号量泄漏问题（严重）

**代码位置**：`interface_can.cpp:194-205`

```cpp
void CanSendMessage(CAN_context* canCtx, uint8_t* txData, CAN_TxHeaderTypeDef* txHeader)
{
    osStatus semaphore_status;
    semaphore_status = osSemaphoreAcquire(sem_can1_tx, osWaitForever);
    //                          ↑ 阻塞等待（无超时）

    if (semaphore_status == osOK)
        HAL_CAN_AddTxMessage(canCtx->handle, txHeader, txData, ...);
        // ↑ 返回值未检查 ★★★
}
```

**关键发现**：STM32F4 HAL 库 `HAL_CAN_AddTxMessage` 在所有 mailbox 满时返回 `HAL_ERROR`（**不是** `HAL_BUSY`）。

```c
// stm32f4xx_hal_can.c:1275-1343
if (((tsr & CAN_TSR_TME0) != 0U) || ...)  // 有空闲 mailbox
    return HAL_OK;                          // 成功
else
    return HAL_ERROR;                       // 全部满 → HAL_ERROR
```

**后果**：
- 如果 `HAL_CAN_AddTxMessage` 返回 `HAL_ERROR`，信号量已经被 `Acquire` 消耗
- `tx_complete_callback`（TX 完成 ISR）永远不会被调用
- `osSemaphoreRelease` 不会执行 → **信号量永久泄漏**
- 后续所有 `CanSendMessage` 调用全部卡死在 `osWaitForever` 上

**触发场景**：mailbox 有 3 个，正常串行发送不会满。但如果有：
1. 实时环（50Hz，`updateCounter % 100 == 0`）发了 7 个位置命令
2. ASCII 线程（`!START`）同时发了使能命令
3. 两者并发争夺同一个 `sem_can1_tx`

此时第 2 个竞争者拿到的 mailbox 可能刚好满了（第 3 个正在发送，第 1 个还没完成）→ `HAL_ERROR` → **信号量泄漏**。

**结论**：**文档 §4 真凶 #2 的描述方向正确（信号量永久泄漏导致系统卡死），但具体机制是 HAL_ERROR 而非 HAL_BUSY。**

### 10.2 `can_protocol.cpp` 状态确认：不是"简化版"

**文档 §2.2 说**："当前 can_protocol.cpp 是简化版（33 行），没有这些处理"

**实际代码**：当前 `can_protocol.cpp` 是 **230+ 行的完整版**，包含：
- `0x5A` 堵转广播处理（`SetStallMode` + `printf`）
- `0x5C` 查询响应处理（`printf`）
- `0x28~0x2B` PID 合并回包（4 次分收后合并 printf）
- `0x2C/0x2D` 加速度/电流缓存（用时间戳解决异步 printf 竞争）
- `0x7C` 旧固件堵转兼容

**文档 §5 待修 #4 需要重新评估**：当前 `can_protocol.cpp` 已经实现了完整功能，但 `printf` 放在 CAN RX ISR 中，存在隐患（见下节）。

### 10.3 ISR 内 printf 真实风险评估

**CAN RX 中断优先级**（`can.c:134`，优先级 5，高于所有 FreeRTOS 任务）：
```c
HAL_NVIC_SetPriority(CAN1_RX0_IRQn, 5, 0);
```

**CAN TX 中断优先级**（`can.c:132`，优先级 5）：
```c
HAL_NVIC_SetPriority(CAN1_TX_IRQn, 5, 0);
```

**UART4 中断优先级**（`usart.c:183`，优先级 6，低于 CAN）：
```c
HAL_NVIC_SetPriority(UART4_IRQn, 6, 0);
```

**printf 路径**（从 `_write` 到 UART DMA）：
1. `_write` 调用 `HAL_UART_Transmit_DMA`
2. UART TX DMA 中断优先级 = 6
3. DMA TX 完成 ISR 调用 `HAL_TIM_PWM_PulseFinishedCallback`（优先级 5）

**实际风险**：
- CAN RX ISR（优先级 5）内调用 `printf("[STALL] node=%d TRIGGER\r\n", ...)` 
- `printf` → `_write` → `HAL_UART_Transmit_DMA`
- 如果此时 UART DMA TX 正在运行，`_write` 会等待 DMA 完成（spin）
- **UART DMA TX ISR** 优先级是 6，**可以**被 CAN RX ISR（优先级 5）抢占
- 但 `printf` 本身有 `__io_lock` 临界区锁，会禁止中断

**结论**：ISR 内 printf **不会直接死锁**，但有以下风险：
1. 每帧堵转广播（0x5A）触发一次 `printf` → 7 个电机 × 堵转 = 大量 ISR printf
2. 如果 `printf` 的临界区锁期间（≈几十 μs）正好有更高优先级的 CAN TX 中断，会增加中断延迟
3. `printf` 的 `__write` 在 DMA 忙时会 spin-wait，轻微影响 ISR 执行时间

### 10.4 `UpdateJointAngles` 轮询频率确认

**触发条件**（`main.cpp:64-66`）：
```cpp
if (updateCounter % 50 == 25) {
    dummy.UpdateJointAngles();
}
```

**实际频率**：
- `updateCounter` 由 TIM7 5kHz 中断驱动（`ulTaskNotifyTake`）
- `updateCounter % 50 == 25` → 5kHz / 50 = 100Hz 触发一次
- 4 组轮询，每组 2 个轴（除了地轨独占 1 组）
- **全量查询周期** = 100Hz / 4 = 25Hz
- **每轴刷新率** = 25Hz

**文档 §4 真凶 #5 描述准确**。

### 10.5 `osDelay(20)` 实际影响

**代码位置**：`main.cpp:221`
```cpp
osDelay(20);  // 设置硬休眠 20ms 以削峰屏刷新占时
```

**实际影响**：
- 每次循环 `osDelay(20)` → 休眠 20ms
- **实际刷新率** = 1 / 0.02s = **50Hz**（不是文档说的 20Hz）
- 旧版 `source code/` 没有这个 `osDelay`
- **结论**：文档 §4 真凶 #4 描述方向正确，但 20ms 对应的是 50Hz 而非 20Hz

### 10.6 `SetEnable` 循环次数确认

**代码位置**：`dummy_robot.cpp:611-631`

```cpp
void DummyRobot::SetEnable(bool _enable)
{
    // ... 预处理 ...
    for (int i = 1; i <= 6; i++)         // ★ 6 个关节
        motorJ[i]->SetEnable(_enable);
    motorJ[0]->SetEnable(_enable);        // ★ 地轨
    hand->SetEnable(_enable);             // ★ 夹爪
    // 共 6 + 1 + 1 = 8 次
}
```

**结论**：文档 §4 真凶 #1 说"一次性循环 7 个电机 + 1 个夹爪 = 8 次"基本正确（6+1+1=8），但循环只处理 6 个关节，地轨和夹爪各单独 1 次，总数 8 次。

### 10.7 HAL 中断优先级与 FreeRTOS 的关系

**优先级配置**：
| 中断 | 优先级 | 说明 |
|---|---|---|
| CAN1 TX/RX/SCE | 5 | 高于 FreeRTOS 任务 |
| TIM7（5kHz 实时环触发）| 5 | 高于 FreeRTOS 任务 |
| UART4 | 6 | 高于 Normal 任务 |
| SysTick | `TickPriority`（configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY 以下）| FreeRTOS 可管理 |

**FreeRTOS 配置**（`FreeRTOSConfig.h`）：`configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY` 通常为 5 或更高。

这意味着 CAN/TIM7 中断（优先级 5）**不受 FreeRTOS 管理**，它们可以打断任何 FreeRTOS 任务，包括 `osDelay`、`osSemaphoreAcquire` 等。
