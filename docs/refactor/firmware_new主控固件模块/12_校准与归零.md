## 1. 问题现象

用户实测（刷入 `firmware_new/dummy-ref-core-fw`）：

```
[18:18:55] [TX] #OFFSET_J all
[18:29:27] [TX] #OFFSET_J 1
```

发送 `#OFFSET` 系列指令后：

- RGB 灯效卡死不刷新
- OLED 显示卡死不刷新
- 机械臂可继续运动（说明系统未真正死机，仅 UI 线程被饿死）

## 2. 新旧 OFFSET 实现差异

### 2.1 旧版：`!CALIBRATION` → `DummyRobot::CalibrateHomeOffset()`

`firmware_old/dummy-ref-core-fw/Robot/instances/dummy_robot.cpp:199-227`

```cpp
void DummyRobot::CalibrateHomeOffset()
{
    // Disable FixUpdate, but not disable motors
    isEnabled = false;              // ① 先禁能主控 5kHz 实时环
    motorJ[ALL]->SetEnable(true);    // ② 但电机保持使能（可手拖）

    motorJ[2]->SetCurrentLimit(0.5);
    motorJ[3]->SetCurrentLimit(0.5);
    osDelay(500);

    motorJ[ALL]->ApplyPositionAsHome();   // ③ 一次广播 6 轴归零
    osDelay(500);

    initPose     = DOF6Kinematic::Joint6D_t(0, 0, 90, 0, 0, 0);
    currentJoints = DOF6Kinematic::Joint6D_t(0, 0, 90, 0, 0, 0);
    Resting();                            // ④ 回 resting 姿态
    osDelay(500);

    motorJ[ALL]->ApplyPositionAsHome();   // ⑤ 二次归零
    osDelay(500);
    motorJ[2]->SetCurrentLimit(1);
    motorJ[3]->SetCurrentLimit(1);
    osDelay(500);

    Reboot();                             // ⑥ 重启所有电机，清内部状态
}
```

关键特征（缺一不可）：

| # | 动作 | 作用 |
|---|---|---|
| ① | `isEnabled = false` | **5kHz 实时环切到 disabled 分支，只发 1 帧 0x23 广播，不再每 20ms 发 7 帧 MoveJoints** |
| ② | `SetEnable(true)`（电机侧） | 保持电机通电，允许手动拖动到零位 |
| ③④⑤ | `osDelay(500)` ×3 | 等电机完成归零动作与 0x23 回包 |
| ⑤ | 二次归零 | 先归零 → 移到 resting → 再归零，保证 resting 姿态下 0x23 角度正确 |
| ⑥ | `Reboot()` | 重启全部电机（+ 夹爪），清 goalPosition/goalVelocity/goalCurrent 等运行态 |

### 2.3 差异汇总

| 维度 | OLD (`!CALIBRATION`) | firmware_new (`#OFFSET_J`) | 后果 |
|---|---|---|---|
| **先禁能主控** | `isEnabled = false` | ❌ 无 | **5kHz 实时环持续 50Hz 发 7 帧 MoveJoints，与 OFFSET 争 CAN** |
| **电机保持使能** | `SetEnable(true)` | ❌ 无 | — |
| **限流** | J2/J3 降到 0.5A | ❌ 无 | 标定时机械臂可能被大力拖动 |
| **等待** | `osDelay(500)` ×3 | ❌ 无 | 主控不等 0x23 回包就 Respond("ok") |
| **二次归零** | 有（归零→resting→再归零） | ❌ 无 | `initPose`/`currentJoints` 与电机实际零位不同步 |
| **`initPose` 同步** | 设为 REST_POSE | ❌ 无 | 归零后主控仍按旧 initPose 做逆解，姿态显示错乱 |
| **Reboot 清状态** | 有 | ❌ 无 | 电机内部 goal/状态残留 |

### 2.4 附带差异：`CanSendMessage` 超时策略

| 版本 | 代码 | 单次最坏阻塞 |
|---|---|---|
| OLD | `osSemaphoreAcquire(sem_can1_tx, osWaitForever)`（`interface_can.cpp:237`） | **无限**（旧版靠 `isEnabled=false` 保证不会被并发卡） |
| firmware_new | mailbox 自旋 5ms + `osSemaphoreAcquire(..., 10)`（`interface_can.cpp:238-265`） | **15ms** |

`#OFFSET_J all` 串行调 6 次 → 单次命令最坏阻塞 **90ms**，全部发生在 `UsbServerTask` 上下文（`osPriorityNormal`）。

## 3. 卡死根因分析

### 3.1 根因：5kHz 实时环（Realtime 优先级）持续抢占 Normal 优先级任务

任务优先级（`firmware_new/dummy-ref-core-fw/UserApp/main.cpp`）：

| 任务 | 优先级 | 频率 | 是否发 CAN |
|---|---|---|---|
| `ControlLoopFixUpdateTask` | `osPriorityRealtime` | 5kHz（TIM7 200μs） | **是（enabled 时 50Hz × 7 帧）** |
| `ControlLoopUpdateTask` | `osPriorityNormal` | 事件触发 | 间接 |
| `OledTask` | `osPriorityNormal` | ~60Hz | 否（I2C） |
| `RGBTask` | `osPriorityNormal` | 33Hz | 否（DMA） |
| `UsbServerTask` | `osPriorityNormal` | 事件触发 | **是（OFFSET 6 帧）** |

实时环 enabled 分支（`main.cpp:57-84`）：

```cpp
case DummyRobot::COMMAND_TARGET_POINT_SEQUENTIAL:
case DummyRobot::COMMAND_TARGET_POINT_INTERRUPTABLE:
case DummyRobot::COMMAND_CONTINUES_TRAJECTORY:
    if (updateCounter % 100 == 0) {          // 50Hz
        dummy.MoveJoints(dummy.targetJoints);              // 6 帧 0x07
        dummy.motorJ[7]->SetPositionWithMotorRps(...);     // 1 帧 0x07
    }
    dummy.UpdateJointPose6D();
    break;
```

**竞争过程**：

1. `UsbServerTask` 收到 `#OFFSET_J all`，进入 for 循环
2. 第 N 次 `CanSendMessage`：mailbox 满 → 自旋最多 5ms
3. 期间 TIM7 触发 → `ControlLoopFixUpdateTask`（Realtime）**抢占** `UsbServerTask`
4. 实时环若命中 `% 100 == 0`，串行发 7 帧 CAN；每帧也走 `CanSendMessage`（自旋 5ms + 等信号量 10ms）
5. Realtime 任务可反复抢占，Normal 任务（`UsbServerTask` / `OledTask` / `RGBTask`）在数百毫秒内得不到调度

### 3.2 为什么 OLED 表现为"不刷新"

`ThreadOledUpdate`（`main.cpp:140-238`）循环体末尾 `oled.sendBuffer()` 通过 `hi2c0` **同步 I2C** 写 1024 字节到 SSD1306（400kHz 下约 25ms）。

- 任务被饿死 → `sendBuffer()` 长期不执行 → 屏上内容冻结在最后一帧
- 若在 I2C 传输中途被抢占导致 HAL 超时 → I2C BUSY 状态后续难以恢复 → 表现同样为彻底不刷新

### 3.3 为什么 RGB 表现为"不刷新"

`ThreadRGBUpdate`（`main.cpp:255-267`）：

```cpp
for (;;) {
    g_rgb_tick++;
    if (rgb.UpdateLoop()) rgb.Run((RGB::Rgb_style_t)dummy.GetRGBMode());
    osDelay(30);
}
```

- 任务被饿死 → `osDelay(30)` 实际变成数百毫秒 → 灯效动画肉眼静止
- WS2812 依赖 TIM2 PWM DMA 逐位发送，长时间不发新帧即视觉上"熄灭/静止"

**注**：`dummy.GetRGBMode()` 读的是 `rgbMode` 字段，只有 `SetEnable()` / `SetRGBMode()` 会改写。`#OFFSET_J` 不碰它，**所以 RGB 卡死纯粹是调度饥饿，不是状态错乱**。

### 3.4 电机侧二次因素（次要，但会加剧问题）

新固件电机端 `Motor::Controller::ApplyPosAsHomeOffset()`（`firmware_new/dummy-motor-fw/Ctrl/Motor/motor.cpp:616+`）新增了：

```cpp
context->config.motionParams.encoderHomeOffset = realPosition % MOTOR_ONE_CIRCLE_SUBDIVIDE_STEPS;
realPosition = context->config.motionParams.encoderHomeOffset;  // 同步归零
realLapPosition = realPosition;
realLapPositionLast = realPosition;
realPositionLast = realPosition;
estPosition = 0;   // 清估算
```

电机端 `realPosition` 被瞬时归零，但主控 `dummy.targetJoints` 仍是归零前的旧目标（`initPose` 未同步）。归零后 5kHz 实时环继续按旧 `targetJoints` 下发，电机会朝"归零前坐标系下的目标"猛冲 —— 这在旧版靠 `initPose = REST_POSE` + `Reboot()` 双重兜底避免，新版两者都没有。

## 4. 待验证假设（可用固件内置心跳计数器实测）

`firmware_new/dummy-ref-core-fw/UserApp/main.cpp:12-18` 已内置 DIAG 计数器：

```cpp
volatile uint32_t g_byte_in, g_line_ready, g_cmd_in, g_cmd_out;
volatile uint32_t g_realtime_tick, g_oled_tick, g_rgb_tick;
```

预期（若根因成立）：

| 现象 | 计数器表现 |
|---|---|
| 命令正常进入 handler | `g_cmd_in` 递增 |
| handler 能返回 | `g_cmd_out` 与 `g_cmd_in` 同步（`CmdExitGuard` RAII 覆盖所有 return 路径） |
| OLED/RGB 被饿死 | `g_oled_tick`、`g_rgb_tick` 增速显著低于 `g_realtime_tick / 100`（Realtime 正常） |
| 硬死机 | 全部计数器同时停止 |

**这排除了"硬 fault / HardFault"的可能**——若为硬死机，所有任务（含 Realtime）会一起停，机械臂也会停转；实测机械臂可动，说明是 Normal 任务被饿死的软饥饿。

## 5. 决策

### 5.1 决策内容

**恢复旧版 `CalibrateHomeOffset()` 的"先禁能再标定"语义。**

具体为：

1. 恢复 `DummyRobot::CalibrateHomeOffset()` 方法（声明 + 实现）
2. `#OFFSET_J all` 改为调用该方法（而非裸循环 `ApplyPositionAsHome()`）
3. `#OFFSET_J <1~6>` 保持单轴归零，但**同样需要先禁能再归零**（单轴同样会在 enabled 态与实时环争 CAN）
4. 保留 v3.2 已生效的"主控不做乐观同步"（电机端已同步 `realPosition`，主控等 0x23 回包）
5. 保留新固件 `CanSendMessage` 的 5ms/10ms 双层超时加固（不退回 `osWaitForever`）

### 5.2 与既有决策的冲突处理

| 既有决策 | 位置 | 处置 |
|---|---|---|
| D1：删除 `!CALIBRATION` 全轴标定 | 模块 12 | **部分推翻**：命令名 `!CALIBRATION` 仍不恢复，但**其内部流程语义由 `#OFFSET_J all` 承载** |
| D2：删除 `DoCalibration()`（0x02） | 模块 12 | **维持**：0x02 是电机端"编码器校准"（标定电流环），与"位置归零"（0x15）不是一回事，不恢复 |
| D3：`#OFFSET_J` 保留 | 模块 12 | **维持** |
| v3.2：删除主控乐观同步 | 模块 12 | **维持**（不冲突） |

### 5.3 理由

- OLD 是默认基线（决策文档 §改造原则 1），本次是第二次因删掉 `isEnabled=false` 而付出代价
- `isEnabled=false` 是**语义正确性**要求，不只是防卡死补丁：归零期间主控不应继续按旧坐标系下发运动指令
- 恢复该语义同时修掉两个问题：UI 饥饿 + 归零后姿态不同步

### 6.2 `CalibrateHomeOffset()` 参考实现

```cpp
void DummyRobot::CalibrateHomeOffset(uint32_t onlyNode)
{
    // ① 先禁能主控实时环（不动电机），5kHz 环切 disabled 分支只发 1 帧 0x23
    bool wasEnabled = isEnabled;
    isEnabled = false;
    commandHandler.ClearFifo();
    osDelay(20);                       // 让实时环跑一轮，确认已切分支

    // ② 保持电机使能，允许手动拖动
    motorJ[ALL]->SetEnable(true);
    osDelay(100);

    // ③ 限流保护（J2/J3 是竖直轴，标定时可能被大力拖动）
    if (onlyNode == 0 || onlyNode == 2) motorJ[2]->SetCurrentLimit_persist(0.5f, false);
    if (onlyNode == 0 || onlyNode == 3) motorJ[3]->SetCurrentLimit_persist(0.5f, false);
    osDelay(100);

    // ④ 第一次归零
    if (onlyNode == 0) { for (int i = 1; i <= 6; i++) motorJ[i]->ApplyPositionAsHome(); }
    else               { motorJ[onlyNode]->ApplyPositionAsHome(); }
    osDelay(500);

    // ⑤ 回 resting 姿态并等到位
    if (onlyNode == 0) {
        initPose      = DOF6Kinematic::Joint6D_t(0, 0, 90, 0, 0, 0);
        currentJoints = DOF6Kinematic::Joint6D_t(0, 0, 90, 0, 0, 0);
        Resting();
        osDelay(500);

        // ⑥ 第二次归零
        for (int i = 1; i <= 6; i++) motorJ[i]->ApplyPositionAsHome();
        osDelay(500);
    }

    // ⑦ 恢复限流
    if (onlyNode == 0 || onlyNode == 2) motorJ[2]->SetCurrentLimit_persist(1.0f, false);
    if (onlyNode == 0 || onlyNode == 3) motorJ[3]->SetCurrentLimit_persist(1.0f, false);
    osDelay(100);

    // ⑧ 重启电机清内部状态
    Reboot();
    osDelay(500);

    // ⑨ 恢复原使能状态
    if (wasEnabled) SetEnable(true);
}
```

### 6.4 实施注意事项

| 事项 | 说明 |
|---|---|
| **总耗时** | `all` 路径 ≈ 2.2s 阻塞。执行上下文是 `UsbServerTask`（Normal），期间阻塞 USB 接收属可接受（旧版同款），但上位机应设超时 ≥3s |
| **两处重复代码** | USB 与 UART4 两份 `#OFFSET_J` 必须**同时改**，否则两条通道语义分叉 |
| **`SetCurrentLimit_persist` vs `SetCurrentLimit`** | 新固件两者并存，`_persist(val,false)` 不写 EEPROM；标定是临时限流，**必须用 `_persist(..., false)`**，否则每次标定都擦写电机 EEPROM |
| **`osDelay(20)` 首步** | `isEnabled=false` 后需让 5kHz 实时环至少跑一轮完成分支切换，否则前 1~2 次 `CanSendMessage` 仍会与实时环争 mailbox |
| **`Reboot()` 范围** | `DummyRobot::Reboot()` 会同时重启 ALL 电机（StdId=0x7F）和夹爪（StdId=(8<<7)\|0x7F）。单轴标定 `onlyNode != 0` 时是否该 Reboot 全部，需实测确认（建议仍全 Reboot，与旧版一致） |
| **`wasEnabled` 恢复** | 旧版 `CalibrateHomeOffset` 结束后不恢复 `isEnabled`（保持 false）。新版建议保存并恢复，避免打断用户当前工作状态 |

## 7. 验证方案

| # | 测试项 | 步骤 | 期望 |
|---|---|---|---|
| 1 | 复现原 bug（基线） | 当前固件，enabled 态发 `#OFFSET_J all` | OLED/RGB 卡死（已知） |
| 2 | 全轴归零 | 修复后，enabled 态发 `#OFFSET_J all` | OLED/RGB **持续刷新**；6 轴归零；约 2~3s 后回 `ok` |

| 5 | 归零后运动 | 归零后发 `>0 0 90 0 0 0` | 机械臂正确运动到 resting，不冲撞、不失控 |

### 7.1 上位机超时调整

`串口助手.py` 侧需把 `#OFFSET_J` 的等待超时从默认（通常 1s）提到 **≥3s**，否则会误判为通信失败并可能重发导致命令堆积。

## 9. 遗留风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| `CanSendMessage` 的 5ms/10ms 超时可能导致归零命令丢帧 | 超时后直接 `return`，0x15 帧丢失而 `Respond("ok")` 已发出 | 归零后由 `Reboot()` 兜底；实施后验证 6 轴是否全部归零 |
| `osDelay` 在 UsbServerTask 上下文阻塞 USB 接收 | 长指令期间 USB 无法收发 | 与旧版行为一致；上位机调超时 |
| `Reboot()` 重启全部电机含地轨与夹爪 | 单轴标定也重启全机 | 与旧版一致；需确认是否有用户态副作用 |
| `initPose` 被强制设为 REST_POSE | 若用户只想归零单轴，改动 `initPose` 会影响其余轴解算 | 6.2 实现中 `initPose` 同步仅在 `onlyNode==0` 分支执行 |
| 文档冲突 | 模块 12 的"禁止恢复 `!CALIBRATION`"需同步更新 | 见 §10 |
