# 机械臂固件代码质量分析报告

**生成时间：** 2026-09-16  
**分析范围：** `firmware/ref_core_f405`（主控）+ `firmware/motor_fw_f103_*`（电机驱动）

---

## 一、架构设计

### 1.1 整体评价：中等偏下

**做得好的地方：**
- 模块层次清晰：BSP → Robot → UserApp 三层
- FreeRTOS 多线程架构合理：5kHz 实时环与命令解析分离
- 运动学 D-H 参数建模正确
- 堵转检测状态机设计思路正确（IDLE → RETREATING → LOCKED）

**主要问题：**

| 问题 | 严重程度 | 说明 |
|------|---------|------|
| 固件多副本 | 🔴 高 | 4 个几乎相同的电机固件（35/42/57/gripper），仅 `configurations.h` 不同，维护成本极高 |
| 代码重复 | 🔴 高 | `can_protocol.cpp` 中 J1~J6、J7、夹爪的处理逻辑完全重复约 400 行 |

| 配置分散 | 🟡 中 | 默认参数在 `motor.h`、`main.cpp`、`interface_can.cpp` 三处定义 |

## 二、主控固件问题（ref_core_f405）

### 2.1 地轨 (J7) 状态未纳入 IsMoving() 🔴 P0

**文件：** `firmware/ref_core_f405/Robot/instances/dummy_robot.cpp`

**问题：** `IsMoving()` 依赖 `jointsStateFlag`，但 `UpdateJointAnglesCallback()` 只处理 J1~J6（`i = 1; i <= 6`），地轨的 FINISH 状态从未被写入该标志位。

```cpp
// dummy_robot.cpp 第 183-196 行
void DummyRobot::UpdateJointAnglesCallback()
{
    for (int i = 1; i <= 6; i++)  // ← 只处理 J1~J6，不处理 J7
    {
        // ...
        if (motorJ[i]->state == CtrlStepMotor::FINISH)
            jointsStateFlag |= (1 << i);
        // ...
    }
    // 地轨位置更新了，但 jointsStateFlag 从未涉及
    currentRailPos = motorJ[7]->angle / 360.0f * 5.0f;
}
```

**后果：** `IsMoving()` 永远只检查 J1~J6 是否到位，地轨到位与否被完全忽略。

**建议修复：**
- 方案 A：在 `jointsStateFlag` 中增加 bit7 表示地轨状态
- 方案 B：单独维护 `railStateFlag`，`IsMoving()` 同时检查两个标志

### 2.2 SEQUENTIAL 模式返回 ok 的时机错误 🔴 P1

**文件：** `firmware/ref_core_f405/Robot/instances/dummy_robot.cpp`

**问题：** SEQUENTIAL 模式下，电机还在转时就直接返回 "ok"，上位机会误以为指令已完成。

```cpp
// dummy_robot.cpp ParseCommand()
if (context->IsMoving() && context->IsEnabled())
{
    Respond(*usbStreamOutputPtr,  "ok");  // ← 问题：电机还在转却返回 ok
    Respond(*uart4StreamOutputPtr, "ok");
    break;
}
context->MoveJoints(context->targetJoints);
// ...
```

**后果：** 上位机收到 "ok" 后立即发下一条指令，但上一条还没执行完，SEQUENTIAL 的"顺序执行"语义被破坏。

---

### 2.3 ServoJ 的 dt 下限 20ms 完全无道理 🟢 P2

**文件：** `firmware/ref_core_f405/Robot/instances/dummy_robot.cpp`

**问题：** `ServoJ` 中用 `micros()` 计算帧间隔，但强制设了 20ms 下限。

```cpp
uint32_t nowUs = micros();
float dt = (nowUs - lastServoTime) / 1000000.0f;
if (dt <= 0.001f) dt = 0.02f;   // ← 20ms 下限，但 5kHz 实际是 0.2ms
```

**后果：** `dt = 0.02f` 把正常 0.2ms 的帧间隔放大 100 倍，导致 `reqSpeed` 计算严重偏低。

---

### 2.4 CAN 发送无软件缓冲 🟡 P1

**文件：** `firmware/ref_core_f405/Bsp/communication/interface_can.cpp`

**问题：** `CanSendMessage` 每次直接操作硬件邮箱，ServoJ 模式（5kHz × 7 电机）下必然大量丢帧。

```cpp
// interface_can.cpp
void CanSendMessage(CAN_context* canCtx, uint8_t* txData, ...)
{
    uint32_t startTick = HAL_GetTick();
    while (HAL_CAN_GetTxMailboxesFreeLevel(canCtx->handle) == 0) {
        if (HAL_GetTick() - startTick > 5) return;  // ← 超时直接丢弃
    }
    // ...
}
```

**建议：** 使用 RingBuffer 缓冲发送请求，发送 ISR 从 buffer 取数据。

---

### 2.5 命令队列满时丢弃旧命令 🟡 P1

**文件：** `firmware/ref_core_f405/Robot/instances/dummy_robot.h`

**问题：** `osMessageQueuePut` 失败时直接返回 `0xFF`，旧命令被静默丢弃。

```cpp
osStatus_t status = osMessageQueuePut(commandFifo, buf, 0U, 0U);
if (status == osOK)
    return osMessageQueueGetSpace(commandFifo);
return 0xFF;  // ← 上位机收到 0xFF 无法区分"队列满"还是"其他错误"
```

## 三、电机固件问题（motor_fw_f103_*）

### 3.1 CloseLoopControlTick() 函数过长 🟡 P1

**文件：** `firmware/motor_fw_f103_35/Ctrl/Motor/motor.cpp`

**问题：** 单个函数超过 300 行，混合了以下职责：
- 位置/速度/力矩控制逻辑
- 堵转检测状态机
- 模式切换处理
- RETREATING/LOCKED 状态处理
- 状态更新

**建议：** 拆分为独立函数：
- `StallDetection()` — 堵转检测
- `RetreatingHandler()` — 回退处理
- `StateUpdate()` — 状态机

---

### 3.2 堵转检测中用 == 比较位置 🟢 P2

**文件：** `firmware/motor_fw_f103_35/Ctrl/Motor/motor.cpp`

**问题：** 到位判断用精确相等，可能永远触发不了。

```cpp
// motor.cpp
bool reachedGoal = (controller->modeRunning == MODE_COMMAND_POSITION) &&
                   (controller->softPosition == controller->goalPosition) &&  // ← 用 ==
                   (controller->softVelocity == 0);                        // ← 用 ==
```

**建议：** 改用容差比较：
```cpp
bool reachedGoal = (abs(softPosition - goalPosition) < POSITION_TOLERANCE)
                && (abs(softVelocity) < VELOCITY_TOLERANCE);
```

---

### 3.3 CAN ISR 中调用 printf 🟢 P2

**文件：** `firmware/motor_fw_f103_35/UserApp/protocols/interface_can.cpp`

**问题：** 在 CAN 接收中断处理函数中调用 `printf`，产生不可预期的实时性问题。

```cpp
// interface_can.cpp
case 0x05:  // Set Position
    printf("SET MOTOR[0x05] POSITION[]\r\n");  // ← 在 ISR 中
```

---

### 3.4 RxData 全局变量 🟡 P1

**文件：** `firmware/motor_fw_f103_35/UserApp/protocols/interface_can.cpp`

**问题：** `RxData` 是全局缓冲区，如果处理逻辑被递归调用或数据被覆盖，会导致数据错乱。

```cpp
switch (_cmd) {
    case 0x03:
        motor.controller->SetCurrentSetPoint((int32_t)(*(float*)RxData * 1000));
        // RxData 全局，可能被覆盖
```

**建议：** 改为栈上局部变量或函数参数传递。

---

### 3.5 默认参数在多处定义不一致 🟡 P1

**文件：** `firmware/motor_fw_f103_35/Ctrl/Motor/motor.h` + `main.cpp`

**问题：** `ratedCurrent` 在两处定义但值不同：

```cpp
// motor.h 构造函数
config.motionParams.ratedCurrent = 1000;  // ← 1000mA

// main.cpp EEPROM 初始化
.currentLimit = 2 * 1000,  // ← 想用 2000mA = 2A
```

**后果：** 实际运行以 EEPROM/boardConfig 为准，但代码阅读时容易混淆。

---

### 3.6 jointAccRuntime 初始值无法区分"未查询"和"实际为0" 🟢 P2

**文件：** `firmware/ref_core_f405/Robot/instances/dummy_robot.h`

**问题：** 数组初值为 0，电机掉线时也保持 0，无法区分"从未查询过"和"查询失败"。

```cpp
float jointAccRuntime[9] = {0};  // ← 初值 0
// 电机掉线 → jointAccRuntime[i] 保持原值（0）
// "未查询过"也显示为 0 → 无法区分
```

## 四、代码风格问题

### 4.1 命名不一致

| 变量 | 说明 |
|------|------|
| `railSpeedRps` vs `jointSpeedRps` | 语义相近但命名风格不同 |
| `AXIS_MAX_RPS[]` | float 数组 |
| `FALLBACK_JOINT_ACCELERATION` | 单个 float 常量 |
| `MOTOR_REDUCTION[8]` | uint8_t 数组 |

**建议：** 统一用 `kebab-case` 或 `snake_case` 命名约定。

---

### 4.2 魔法数字

**示例：**
```cpp
if (updateCounter % 100 == 0)   // 为什么是 100？
if (updateCounter % 50 == 25)  // 为什么是 25？
```

**建议：** 定义宏或枚举：
```cpp
#define CMD_UPDATE_DIVISOR   100    // 5kHz / 100 = 50Hz
#define ANGLE_UPDATE_OFFSET  25    // 与 CMD_UPDATE 错开半拍
```

---

### 4.3 4 个电机固件几乎完全重复

| 固件 | 路径 | 唯一区别 |
|------|------|----------|
| 35电机 | `motor_fw_f103_35/` | J4~J6 |
| 42电机 | `motor_fw_f103_42/` | J1~J3 |
| 57电机 | `motor_fw_f103_57/` | 地轨 |
| 夹爪 | `motor_fw_f103_gripper/` | 夹爪独立固件 |

**问题：** 4 个固件各自一套完整代码，仅 `configurations.h` 中的电机参数不同。修改一处 bug 需要在 4 个地方同步修改。

**建议：** 合并为一份固件，通过 `configurations.h` 中的宏定义切换电机类型（35/42/57/GRIPPER），减少 75% 的维护成本。

## 六、总结

这个固件在功能实现上是完整的，核心架构基本合理，但代码处于"**能跑但难以维护**"的状态。

**最大问题：**
1. **4 个电机固件重复** — 维护成本极高，修改一处需要同步 4 处
2. **地轨状态被排除在运动完成判断之外** — 堵转检测功能不完整
3. **版本补丁标记满天飞** — 代码被打满补丁，新人阅读困难

建议优先解决这三个 P0 问题，再逐步改善其他问题。
