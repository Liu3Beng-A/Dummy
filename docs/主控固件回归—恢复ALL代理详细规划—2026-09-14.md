# 主控固件回归 — 恢复 ALL 代理

> **状态**：规划文档 
>
> **变更要点**：
>
> - **R2 增补"R2.5 全量改名映射表"** —— 原版只列举了 `Reboot/SetEnable/UpdateAngle` 三处改名，遗漏了 `motorJ[0]` 在 `SetPositionWithMotorRps/SetCurrentSetPoint/QueryAcceleration/QueryStallStatus/angleLimitMax` 等共 ~16 处的调用。如不补齐，**机械臂完全不能动**（MoveJ/MoveL/Homing/Resting/力矩模式全部失效）。

> - **R5 增补"7 节点回包总线仲裁风险提示"** —— 旧版 6 节点就有此问题，新增 1 个地轨不会显著恶化，但要意识到。
> - **R8 改写** —— 原版误以为 `can_protocol.cpp` 是简化版（33 行）需新增 `id==9` 路由分支。实际上当前已是 230+ 行完整版，`id==9` 路由**已完整存在**。R8 不是"新增"，而是"跟随 R2.5/R2 改名后的全量替换"（共 ~12 处）。
> - **R10 加强** —— 在"失败时释放信号量"基础上，增加 `HAL_CAN_GetTxMailboxesFreeLevel` 预检查 + 10ms 超时替代 `osWaitForever`。
> - **R11（新增）`!STOP` 急停独立 bug** —— 主控 `BroadcastEStop` 写死 StdId=0x89，电机端解析为 `id=1/cmd=0x09`，但电机固件无 `case 0x09`，加上注释中"0x80~0xBF 广播区间"与代码实际 `cmd >= 0x50` 的判断自相矛盾——`!STOP` 帧**0 个电机响应**（连 J1 也丢）。`EmergencyStop()` 后续 3 行副作用（`jointsStateFlag=0` + `isEnabled=false` + `ClearFifo`）掩盖了真实状态，导致空闲态发 STOP 看似成功、HOME/RESET 中发 STOP 电机仍跑完剩余轨迹。与本次主线（恢复 ALL）正交，作为可选修复项记录。

## 一、问题

### 1.1 症状

`!START` 后 RGB 灯效卡死、串口无响应。电机能响应使能。

### 1.2 根因

`DummyRobot::SetEnable` 在 v2.7/v2.8 重构中将 1 帧 CAN 广播使能（ALL 代理）改为 8 次串行 `CtrlStepMotor::SetEnable` 调用（6 个关节 + 地轨 + 夹爪）。ASCII 线程最长阻塞 ~240ms。叠加 5kHz 实时环与信号量争夺：

- **真凶 #1**：8 次 `osWaitForever` 串行等待 `sem_can1_tx`，阻塞 ASCII 线程最坏 240ms。
- **真凶 #2**：`CanSendMessage` 不检查 `HAL_CAN_AddTxMessage` 返回值。STM32 HAL 在 mailbox 满时返回 `HAL_ERROR`（实测非 `HAL_BUSY`），信号量已 `Acquire` 但 TX 完成 ISR 永不触发 → **信号量永久泄漏 → 死锁**（修正原 §4.4"自旋"描述；自旋会耗 CPU，但 `osWaitForever` 阻塞时让出 CPU 是 FreeRTOS 标准行为）。
- **真凶 #3**：电机端 v3 堵转检测使能时回投 CAN 总线，主控简化接收路径放过 0x5A（不感知堵转），但不影响使能路径。

### 1.3 修复方向

恢复 ALL 代理（覆盖 J1~J6 + 地轨）+ 夹爪独立指针 + 修信号量：

| 操作 | 当前实现 | 修复后 | 帧数对比 |
|------|----------|--------|---------|
| `SetEnable(true)` | 8 次串行 CAN 0x01 | **2** 帧 CAN：`motorJ[ALL]` + `hand` | 8 → 2 |
| `Reboot()` | 8 次串行 | **2** 帧：`motorJ[ALL]` + `hand` | 8 → 2 |
| `UpdateAngle()` | 4 组轮询 | **1** 帧：`motorJ[ALL]` 广播查询 | 4 → 1 |
| ASCII 线程最长阻塞 | ~240ms | ~5ms | -235ms |

## 二、ALL 代理机制

### 2.1 电机端 CAN filter 配置

所有电机端 CAN filter 配置为全接收（Filter=0/Mask=0），可接收任意 StdId。

```c
sFilterConfig.FilterIdHigh     = 0x0000;
sFilterConfig.FilterIdLow      = 0x0000;
sFilterConfig.FilterMaskIdHigh = 0x0000;
sFilterConfig.FilterMaskIdLow  = 0x0000;
```

→ 任何 StdId 都被电机端 CAN 控制器接收。

### 2.2 ALL 代理原理

主控代码：

```cpp
motorJ[ALL] = new CtrlStepMotor(hcan, 0, false, 1, -180, 180);
motorJ[ALL]->SetEnable(true);
```

`CtrlStepMotor::SetEnable` 内部：

```cpp
txHeader.StdId = nodeID << 7 | mode;  // 0 << 7 | 0x01 = 0x01
// ... 发 1 帧 CAN, StdId=0x01
```

电机端如果保留 `id == 0` 特判：

```c
uint8_t id  = (RxHeader.StdId >> 7);
uint8_t cmd = (RxHeader.StdId & 0x7F);
if (cmd >= 0x50 && cmd != 0x5C) {
    OnCanCmd(cmd, RxData, RxHeader.DLC);   // 广播分支（cmd ≥ 0x50）
}
else if (id == 0 || id == boardConfig.canNodeId) {  // 普通命令 + id==0 特判
    OnCanCmd(cmd, RxData, RxHeader.DLC);
}
```

→ 1 帧 StdId=0x01 即可被所有电机识别为广播，所有节点响应。

### 2.3 实施前提（关键）

**新版电机固件已删除 `id == 0` 特判**，必须恢复（见 R9）。否则 ALL 代理的 StdId=0x01 帧被电机端丢弃，`!START` 等命令完全失效。

新版的 0x23 单播查询（`motorJ[ALL]->UpdateAngle()`）生成的 StdId=0x23 因 cmd=0x23 < 0x50，会走 `else if (id == 0 || ...)` 分支，同样需要 R9 恢复 `id == 0` 特判。

## 三、最终设计

### 3.1 对象层

```cpp
class DummyRobot {
    CtrlStepMotor* motorJ[7] = {nullptr};
    // motorJ[0]=ALL(广播代理,ID=0), motorJ[1..6]=J1~J6(ID=1~6)
    // ★ 关键：motorJ[0] 不再是地轨
    CtrlStepMotor* rail = nullptr;   // 地轨独立指针（ID=9；接管原 motorJ[0] 的全量功能）
    StepHand* hand = {nullptr};      // 夹爪独立指针（ID=8，不在 ALL 范围）
};
```

**关键点（v2 修订）**：

- `motorJ[]` 数组大小保持 **7**（`motorJ[0..6]` = ALL + J1~J6）
- `motorJ[ALL]` 通过 `nodeID=0` 编码 1 帧广播覆盖 **J1~J6 + 地轨**（ID=1~6, 9，共 7 个节点）
- `rail` 是独立指针，仿 `hand` 模式；
- `rail` 接管**原 `motorJ[0]`（地轨）的全部功能**：发位置（CAN 0x07）、发电流（CAN 0x03）、发查询（CAN 0x2C/0x2D/0x5C）、PID 设置/查询（CAN 0x17~0x1A, 0x28~0x2B）、加速度/电流限幅（CAN 0x12, 0x14）、限位检查（`angleLimitMax/Min`）、状态字段、`Reboot` 的 ASCII 单轴命令
- `rail` 的 `SetEnable`（CAN 0x01）和 ASCII `#REBOOT 9` 的批量 `Reboot` 走 ALL 代理，自己**不**单独发这些命令（地轨被 ALL 覆盖）
- `rail` 的 `Reboot()`（`CtrlStepMotor::Reboot`）单轴方法从主控 `Reboot()` 路径走 ALL 代理；ASCII `#REBOOT 9` 的地轨分支也走 ALL 代理（详见 R2.5）
- `hand` 不在 ALL 范围：`hand` 单独 1 帧 CAN 0x01 发往 ID=8
- ⚠️ **背景**：旧版 `source code/dummy-ref-core-fw` 的 `motorJ[7] = {ALL, J1, J2, J3, J4, J5, J6}`，**无地轨**（旧架构 6 自由度，无地轨轴）。本次重构本质上是"用新引入的地轨轴改造 ALL 代理方案"。

### 3.2 广播机制对照

| 广播类型 | 触发 | 机制 | StdId | 接收节点 |
|---------|------|------|-------|---------|
| **ALL 代理** | `!START` / `!DISABLE` / `!REBOOT` / 位置轮询 | `motorJ[ALL]`（nodeID=0） | 0x01 / 0x7F / 0x23 | J1~J6 + 地轨（ID=1~6, 9） |
| **专用广播帧** | `!STOP`（急停）/ `!STALL_UNLOCK` | 直接写死 StdId | 0x89 / 0x5B | 0x89：❌ 0 节点响应（见 R11-A）；0x5B：✅ 全节点 |

**注意**：原"专用广播帧 → 全节点"的表述对 0x89 不成立——`BroadcastEStop()` 发 StdId=0x89 在电机路由层被静默丢弃（R11-A 详细分析），实际 0 个电机收到 STOP 命令。仅 0x5B（`BroadcastUnlock()`）真正生效。

专用广播帧不依赖 ALL 代理：`BroadcastEStop()` / `BroadcastUnlock()` 是独立函数。

**注意**：`motorJ[ALL]->UpdateAngle()` 发 StdId=0x23 触发 7 个电机同时回包（CAN 总线按 StdId 仲裁，重试 1~2 次）。这是可接受的（旧版 6 节点同样存在），主控 `UpdateJointAnglesCallback` 按 id 分发到 `motorJ[id]` 或 `rail`。

### R5：UpdateJointAngles 改用 ALL（v2 增补风险提示）

**文件**：`firmware/ref_core_f405/Robot/instances/dummy_robot.cpp::DummyRobot::UpdateJointAngles`

**旧**（4 组轮询，每轴 25Hz）：

```cpp
void DummyRobot::UpdateJointAngles()
{
    static uint8_t group = 0;
    switch (group) {
        case 0: motorJ[1]->UpdateAngle(); motorJ[2]->UpdateAngle(); break;
        case 1: motorJ[3]->UpdateAngle(); motorJ[4]->UpdateAngle(); break;
        case 2: motorJ[5]->UpdateAngle(); motorJ[6]->UpdateAngle(); break;
        case 3: motorJ[0]->UpdateAngle(); break;
    }
    group = (group + 1) % 4;
}
```

**新**（1 帧广播查询全部 7 个节点）：

```cpp
void DummyRobot::UpdateJointAngles()
{
    motorJ[ALL]->UpdateAngle();  // 1 帧广播查询 J1~J6 + 地轨（共 7 个回包）
}
```

回包由 R8 路由分发到 `motorJ[1..6]` 或 `rail` 的 `UpdateAngleCallback`。

> **v2 风险提示**：7 个电机同时回包 0x23，CAN 总线按 StdId 仲裁可能重试 1~2 次（id 越小的回包优先）。`UpdateJointAnglesCallback` 在同一 tick 内被每个回包 ISR 调用一次，回包延迟加大时 `currentJoints[]/currentRailPos` 可能在主循环读到"部分回包"的状态（旧版 6 节点已有此问题）。可接受的取舍，未来如需恢复 4 组轮询性能，只需把 `UpdateJointAngles()` 内 1 行换回 switch 即可。

### R10（前置）：`CanSendMessage` 信号量泄漏修复（v2 加强版）

**文件**：`firmware/ref_core_f405/Bsp/communication/interface_can.cpp::CanSendMessage`

HAL 库 `HAL_CAN_AddTxMessage` 在 mailbox 满时返回 `HAL_ERROR`（不是 `HAL_BUSY`，实测 stm32f4xx_hal_can.c:893-950），不释放信号量会导致永久死锁。

**基础修复（v1 已有，必做）**：

```cpp
void CanSendMessage(CAN_context* canCtx, uint8_t* txData, CAN_TxHeaderTypeDef* txHeader)
{
    if (osSemaphoreAcquire(sem_can1_tx, osWaitForever) == osOK) {
        HAL_StatusTypeDef ret = HAL_CAN_AddTxMessage(...);
        if (ret != HAL_OK) {
            osSemaphoreRelease(sem_can1_tx);  // ★ 失败时释放信号量
        }
    }
}
```

**加强版（v2 推荐）**：增加预检查 + 超时，进一步降低触发概率：

```cpp
void CanSendMessage(CAN_context* canCtx, uint8_t* txData, CAN_TxHeaderTypeDef* txHeader)
{
    // ★ 加固#1：发送前查 mailbox 空闲，避免 Acquire 后失败导致信号量浪费
    uint32_t startTick = HAL_GetTick();
    while (HAL_CAN_GetTxMailboxesFreeLevel(canCtx->handle) == 0) {
        if (HAL_GetTick() - startTick > 5) {
            return;  // 5ms 还腾不出 mailbox，放弃本次发送
        }
    }
    
    // ★ 加固#2：10ms 超时替代 osWaitForever，避免永远阻塞
    osStatus semaphore_status;
    if (canCtx->handle->Instance == CAN1)
        semaphore_status = osSemaphoreAcquire(sem_can1_tx, 10);
    else if (canCtx->handle->Instance == CAN2)
        semaphore_status = osSemaphoreAcquire(sem_can2_tx, 10);
    else
        return;

    if (semaphore_status == osOK) {
        HAL_StatusTypeDef ret = HAL_CAN_AddTxMessage(
            canCtx->handle, txHeader, txData, &canCtx->last_heartbeat_mailbox);
        if (ret != HAL_OK) {
            osSemaphoreRelease(sem_can1_tx);  // 失败时释放
        }
    }
    // semaphore_status != osOK 表示超时：放弃本次发送，下一循环重试
}
```

**v2 说明**：基础版只保证"不死锁"；加强版进一步降低触发概率（预检查拦截大部分场景），并且 10ms 超时让"信号量泄漏"真的发生时也能恢复（虽然这种情况现在不会发生，因为基础版已修复）。建议采用加强版。

### R11（v2 新增）：`!STOP` 急停独立 bug（可选修复，不在主线）

> 与本次主线（恢复 ALL + 修信号量）正交，作为独立 bug 记录。如要修复，建议在 R11 实施。

#### R11-A: 问题

主控 `CtrlStepMotor::BroadcastEStop()` 直接写死 `StdId = 0x89`，不经 ALL 代理：

```cpp
// ctrl_step.cpp
void CtrlStepMotor::BroadcastEStop()
{
    txHeader.StdId = 0x89;  // 直接写死
    uint8_t buf[8] = {0};
    CanSendMessage(get_can_ctx(hcan), buf, &txHeader);
}
```

电机端 Rx 路由（`motor_fw_f103_35/Core/Src/can.c:189-211`，35/42/57/gripper 同构）解析：

```c
uint8_t id  = (RxHeader.StdId >> 7);   // 0x89 >> 7  = 1
uint8_t cmd = (RxHeader.StdId & 0x7F); // 0x89 & 0x7F = 0x09   ← 关键

if (cmd >= 0x50 && cmd != 0x5C) { ... }       // cmd=0x09 < 0x50, 不走广播分支
else if (id == boardConfig.canNodeId) { ... } // id=1 → 只有 J1 进入单播分支
```

**对 `StdId=0x89` 的实际处理结果**：

| 电机 | canNodeId | Rx 路由走向 | OnCanCmd 调用 | 电机端 case | 最终结果 |
|---|---|---|---|---|---|
| J1 | 1 | id==nodeID → 单播分支 | `OnCanCmd(0x09)` | `case 0x09` **不存在**（switch 仅识别到 `case 0x89`） | **丢弃** |
| J2~J6 | 2~6 | id≠nodeID | 不调用 | — | **丢弃** |
| 地轨 | 9 | id≠nodeID | 不调用 | — | **丢弃** |
| 夹爪 | 8 | id≠nodeID | 不调用 | — | **丢弃** |

**结论**：`!STOP` 急停帧**没有任何电机响应**，不是"只对 J1 生效"。

**根因 1：代码注释与实现自相矛盾**

`BroadcastEStop()` 注释写"落入电机端广播区间 0x80~0xBF，所有电机节点无条件响应"，但电机实际代码用 `cmd >= 0x50` 判断广播。**11-bit StdId 用 `(nodeID<<7)|cmd` 编码时 cmd 只有 7 bit（0x00~0x7F）**，根本不存在 0x80~0xBF 区间。这是编码设计阶段就形成的错误。

**对比参考 — `BroadcastUnlock()` 的成功路径**：

```cpp
void CtrlStepMotor::BroadcastUnlock()
{
    txHeader.StdId = 0x5B;  // (0<<7)|0x5B, cmd=0x5B ∈ 广播区间 0x50~0x7F
    // ...
}
```
0x5B 的 cmd=0x5B 真正落在广播区间，所有电机响应 `case 0x5B`，UNLOCK 能正常工作。

**根因 2：`EmergencyStop()` 后续 3 行的副作用掩盖真实状态**

```cpp
void DummyRobot::CommandHandler::EmergencyStop()  // dummy_robot.cpp:749-757
{
    context->motorJ[1]->BroadcastEStop();  // 0x89 帧（已被电机丢弃，见根因 1）
    context->jointsStateFlag = 0;          // ← 掩盖电机真实状态，IsMoving() 假返 false
    context->isEnabled = false;             // ← 停止 5kHz 实时环下发新位置，但不直接抱闸电机
    ClearFifo();                            // ← 清指令队列
}
```

- `isEnabled=false` 只让 5kHz 实时环（`main.cpp:35-58`，检查 `dummy.IsEnabled()`）不再下发新位置命令
- 但电机继续执行**最后一次下发的位置命令**——机械臂在 HOME/RESET 中发 STOP 时仍会跑完剩余轨迹
- `jointsStateFlag=0` 让 `IsMoving()`（`dummy_robot.cpp:675-677`，基于 `jointsStateFlag != 0b1111110`）返回 false，掩盖电机真实运行状态

**现象 A — 空闲态发 `!STOP`**：机械臂静止时（电机已 FINISH）发 STOP，`EmergencyStop()` 立即返回 `"ok"`。表面"急停成功"，实际电机本来就在 FINISH 状态，`!STOP` 没起任何作用——这种"假成功"掩盖了真实 bug。

**现象 B — `!HOME` / `!RESET` 中发 `!STOP`**：电机 RUNNING 时发 STOP，`isEnabled=false` 停止 5kHz 环下发新位置，但电机继续执行最后一次下发的 home/rest 目标，机械臂物理上跑到 home/rest 才停。

#### R11-B: 修复方案（任选其一）

**方案甲**（推荐，最小改动）：让 `!STOP` 路径走 ALL 代理：

```cpp

```

此时电机端需要 `id == 0` 特判（R9 已加）。在电机端逻辑里：
```c

```
**`id=0, cmd=0x09 < 0x50`** → 走 id==0 分支 → **所有电机都响应 ✓**

**方案乙**（更彻底，改 StdId 而非改路由）：让主控 `BroadcastEStop()` 发真正落入广播区间 `0x50~0x7F` 的 StdId，电机端加对应 `case` 处理——无需 R9 的 `id==0` 特判，也无需改 Rx 路由逻辑：


**注意**：方案乙中原始提到的"`cmd >= 0x80` 广播响应"在 11-bit StdId `(nodeID<<7)|cmd` 编码下**不可行**——cmd 字段只有 7 bit（0x00~0x7F），根本不存在 cmd=0x80~0xBF 的命令码。改为改主控 StdId 到 0x50~0x7F 区间内的空闲命令码（推荐 0x5D，与 0x5A/0x5B/0x5C 邻近便于阅读）。
