## 2. 核心工程经验(可复用)

### 2.1 依赖关系图先于代码

**做法**：先画"任务依赖关系图"(L0→L1→L2),确定执行顺序,再写代码。

**收益**：
- T3 / T4 无依赖,可以并行开发
- T1 / T2 无依赖,可以并行开发
- T9 是"集成节点",必须等所有底层完成
- 整个项目按"电机 → 主控底层 → 主控应用 → 主控协议 → 串口助手"5 步推进,无阻塞

**模式总结**：
```
L0 基础设施(无依赖,可并行)
  ↓
L1 业务实现(依赖 L0,串行)
  ↓
L2 集成验证(依赖 L1,串行)
```

**复用建议**：任何超过 5 个任务的重构,先花 30 分钟画依赖图。

---

### 2.2 每个任务"三独立"原则

**三个独立**:
- ✅ **可独立编译** —— 最小化依赖链,每个 commit 后 `ninja` 必须通过
- ✅ **可独立 review** —— commit 粒度对应任务编号,reviewer 一眼看清改了什么
- ✅ **可独立回滚** —— `git revert HEAD` 一键回退,不破坏后续任务

**实战案例**：
- T1 + T2 是 4 份电机固件独立改 → 4 个独立 commit → 任一份出问题只回滚那份
- T6 / T7 都是 ASCII 协议改动,涉及 2 处解析块 → 模板代码明确标注"4 处都要改"
- T10 删 `railAcc_mm_s2` 字段 → 必须 T7 先完成(ASCII 不再调 `SetRailAcc`)

**踩过的坑**：T8 一开始是独立任务,后来发现和 T6 在同一处修改 → 立即合并,避免一个 commit 包含两个不相关改动。

**复用建议**：每个 commit 前问自己——"如果这个 commit 失败,能否 revert 不影响其他任务?" 不能则拆分。

### 2.3 EEPROM 字段顺序变化的高风险对策

**问题**：`railAcc_mm_s2` 是 `EepromConfig` 结构体的尾部字段,删除后:
- 前面字段偏移**不变**(`railSpeed_mm_s` 仍能读出)
- 但 `EEPROM_MAGIC` 校验可能失败(老设备版本不同) → 失败时 `LoadConfig` **清空整个 EEPROM**

**对策**:
1. **好消息识别**:尾部字段删除是**安全的** —— 验证字段偏移,确认无副作用
2. **风险沟通**:在文档中明确"升级后第一次上电需手动重存"
3. **可选优化**(本次不做):magic 校验宽容(读取多字段后求校验和)

**模式总结**:结构体字段删除/重排前,必须画**字段偏移图**,标明"安全区"(尾部)和"危险区"(中部)。

**复用建议**：任何涉及 EEPROM/Flash 持久化的字段改动,先用 ASCII 图画出字段布局。

### 2.4 函数签名变化 + 默认参数

**做法**: `SetAcceleration(float _val)` → `SetAcceleration(float _val, bool persist = true)`

**收益**:
- **旧调用方**零修改(默认 `persist=true`)
- **新调用方**显式传 `persist=false` 表示"临时值"

**实战案例**:
- `dummy_robot.cpp:436` 内部调用必须显式传 `false`(临时值不写 EEPROM)
- ASCII 命令按用户传入的 `&` 决定 `persist`

**踩过的坑**:函数签名变化 → 编译会失败 → 所有遗漏点自动暴露。**编译验证 = 最强的一致性检查**。

**复用建议**：C++ 函数加新参数必用**默认参数**,让改动局部化。

---

### 2.5 ASCII 协议"两处解析块"的对称修改

**问题**:`ascii_protocol.cpp` 有**两个独立 ASCII 解析块**(line ~460-600 和 line ~960-1170),每个块都有 `#ACC_J` / `#I_LIMIT_J` / `#ACC_RAIL`。

**风险**:改一处忘改另一处 → 行为不一致 → bug 难定位。

**对策**:
- 模板代码明确标注"两处都改"
- 第一处和第二处的**节点处理范围不同**(第一处有 8=夹爪,第二处只有 1~6)
- 编译后人工核对"4 处 #ACC_J 是否都被改"

**模式总结**:**对称代码 = 风险源**。识别对称代码后,改一处必须改全部,且文档明确标注。

**复用建议**：grep 命令验证对称修改:
```bash
grep -n "#ACC_J" ascii_protocol.cpp
grep -n "#I_LIMIT_J" ascii_protocol.cpp
# 期望:每条命令都出现 2 次(line 460-600 和 960-1170)
```

### 2.7 已知 bug 的"标记但不修"策略

**做法**:B1 (`#SPEED_J` 每次都写 EEPROM) 是已知 bug,但本次**不修**:
- 用户决策:串口助手**没有 `#SPEED_J` 按钮**(grep 验证 0 处匹配)
- 实际影响为零

**模式总结**:**不是所有 bug 都值得修**。修复一个 bug 的成本(代码改动 + 测试 + 回归风险)可能 > bug 本身的影响。

**判断标准**:
- 影响面有多大?(用户是否触发?)
- 修复成本有多高?(代码改动 + 测试成本)
- 是否阻塞其他工作?

**本次案例**:`#SPEED_J` 影响 = 0(没人用),修复成本 = 中(改 `SetVelocityLimit` 签名),结论 = 不修。

**复用建议**：建立"已知 bug 列表"(`ISSUES.md`),明确标注"本次不修"+ 原因。定期 review。

### 2.8 单位与精度的设计权衡

**问题**:`boardConfig.velocityAcc` 是"步/s²",但用户接口用"圈/s²"。

**做法**:查询时除 `MOTOR_ONE_CIRCLE_SUBDIVIDE_STEPS`:
```cpp
tmpF = (float) boardConfig.velocityAcc / (float) motor.MOTOR_ONE_CIRCLE_SUBDIVIDE_STEPS;
```

**模式总结**:**底层存原始单位,接口层做单位转换**。
- 底层(`boardConfig.velocityAcc`):步/s²(精度最高)
- 接口(`#GETJACC`):圈/s²(用户友好)
- 转换放在查询时(不修改存储)

**复用建议**：任何带单位的物理量,底层用 SI 单位 + 整数存储,接口层做浮点转换。

---

### 2.9 串口丢帧与 CRC 校验

**问题**:二进制协议必须校验传输完整性。

**做法**:1 字节 XOR 校验(简单实现):
```cpp
uint8_t crc = 0xAA ^ cmd;
for (int i = 0; i < payload_len; i++) crc ^= payload[i];
```

**模式总结**:**CRC 不是越复杂越好,够用就行**。
- 1 字节 XOR:实现 5 行,能检出 99.6% 单字节错误
- CRC8:实现 30 行,能检出 99.99% 错误
- 对于串口场景(物理层已有 UART 校验),1 字节 XOR 已够

**复用建议**：根据可靠性需求选 CRC 复杂度,不要过度设计。

## 4. 风险与对策(实战验证)

### 4.1 🔴 高风险:EEPROM 字段顺序变化(T10)

**问题**:
```
旧 EEPROM 布局(EEPROM.put(0, config)):
┌─────────────────────────────────────┐
│ magic (uint32)                       │
│ static_r/g/b[3]                      │
│ rgbBrightness + rgbStateStart/Enable/Disable │
│ jointAccBases[6]                     │
│ railSpeed_mm_s ← 偏移 X              │
│ railAcc_mm_s2 ← 偏移 Y (要删)        │
└─────────────────────────────────────┘

新 EEPROM 布局:
┌─────────────────────────────────────┐
│ magic (uint32)                       │
│ static_r/g/b[3]                      │
│ rgbBrightness + rgbStateStart/Enable/Disable │
│ jointAccBases[6]                     │
│ railSpeed_mm_s ← 偏移 X (不变)       │
│ railAcc_mm_s2 ← 删了                │
└─────────────────────────────────────┘
```

**好消息**:`railAcc_mm_s2` 是**尾部字段** —— 删它不影响前面字段偏移 —— `railSpeed_mm_s` 仍能正确读出。

**对策**:
1. **升级后第一次上电** —— 用户手动调一次 `#SPEED_RAIL X &` 重存 EEPROM
2. **发版说明** —— 明确告知"升级后重新设置速度"
3. **可选优化**(不在本次重构范围)—— magic 校验宽容(如读取多字段后求校验和)

**实战结果**:用户按对策 1 操作,顺利升级,无功能损失。

### 4.2 🟡 中风险:SetAcceleration 签名变化(T3)

**问题**:`SetAcceleration(float)` → `SetAcceleration(float, bool)` —— **所有调用方都要传 persist**。

**调用方清单**:
- `dummy_robot.cpp:436` —— `SetJointAcceleration` 内部(必须加 `false`)
- ASCII 命令 `#ACC_J` 两处(T6 处理)
- ASCII 命令 `#ACC_RAIL` 两处(T7 处理)

**对策**:编译验证能查出所有遗漏 —— `ninja` 失败 = 遗漏。

**实战结果**:T3 commit 后 `ninja` 一次性失败 → 定位 `dummy_robot.cpp:436` → 加 `false` → 通过。

### 4.3 � 中风险:ASCII 命令分两处解析(T6 + T7)

**问题**:`ascii_protocol.cpp` 里有**两个独立的 ASCII 解析块**(line ~460-600 和 line ~960-1170),每个块都有 `#ACC_J` / `#I_LIMIT_J` / `#ACC_RAIL`。

**对策**:

- 编译后人工核对"4 处 #ACC_J 是否都被改"

**实战结果**:第一处和第二处模板代码分别粘贴,人工核对 OK。

### 4.4 🟡 中风险:0x2C/0x2D 响应格式

**问题**:电机回包数据格式必须和主控解析对齐。

**格式约定**:
- 0x2C:`data[0..3]` = `float`(圈/s²,已除 `MOTOR_ONE_CIRCLE_SUBDIVIDE_STEPS`)
- 0x2D:`data[0..3]` = `float`(A,已除 1000)

**对策**:
- T1 / T2 模板代码使用相同结构(除数和换算)
- T9 主控直接 `*(float*)data` 读取并 printf —— 不再做二次换算

**实战结果**:实测 4 份电机固件回包格式完全一致。

### 4.5 🟢 低风险:B1 (#SPEED_J) bug 标记为"已知 bug,本次不修"

**问题**:`SetVelocityLimit` 当前 `canBuf[4]=1` 硬编码 —— 每次 `#SPEED_J` 都写 EEPROM。

**对策**:
- **不修**(用户 2026-08-07 01:21 决策)
- 串口助手**没有 `#SPEED_J` 按钮**(grep 验证 `SPEED_J` 0 处匹配)
- 实际影响为零

**实战结果**:重构完成后 grep 验证 0 处 `#SPEED_J` 按钮,确认无影响。

### 4.6 🟢 低风险:夹爪电机不需要 0x2C/0x2D 处理(T9)

**问题**:id==8 是夹爪 —— 现状 `can_protocol.cpp` 中 `id==8` 只处理 0x23 / 0x25。

**对策**:
- T9 **不加** `id==8` 的 0x2C/0x2D 处理
- 串口助手发 `#GETJACC 8` → 电机回 0x2C → **主控忽略**(无对应 case)
- 用户层面:"夹爪不需要查加速度/电流" —— 设计上不暴露

## 9. 术语表

| 术语 | 含义 |
|---|---|
| **主控** | STM32F405RG(ref_core_f405)—— 中央控制器 |
| **电机固件** | STM32F103CBT6(motor_fw_f103_35/42/57/gripper)—— 电机驱动板 |
| **5kHz 环** | 电机固件的位置控制循环(每 200μs 跑一次) |
| **CAN StdId** | 标准帧 ID 格式:`StdId = (nodeID << 7) \| cmdCode` |
| **nodeID** | 电机节点 ID(地轨=9、关节=1~6、夹爪=8) |
| **cmdCode** | CAN 命令码(0x00~0x7F 普通,0x80~0xBF 广播) |
| **canBuf[4]** | 电机固件 0x12/0x14 命令的第 5 字节,标记是否写 EEPROM(0=不写,1=写) |
| **EEPROM 写入** | STM32F103 内部 flash 写入,擦写寿命 ~10,000 次 |
| **fiber 协议** | 基于 libfibre 的 RPC 协议(`set_joint_acc` 等) |
| **0x2C / 0x2D** | 新增 CAN 命令码 —— 查询加速度 / 查询电流限幅 |
| **MOTOR_ONE_CIRCLE_SUBDIVIDE_STEPS** | 每圈步数 = 200 × 256 = 51200(电机内部常数) |
| **jointAccBases** | 主控基础加速度数组 `{150, 100, 200, 200, 200, 200}`(开发者实测) |
| **railSpeed_mm_s** | 地轨速度字段(mm/s)—— 保留 + EEPROM 存 |
