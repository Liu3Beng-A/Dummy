## 逐项验证

### ✅ 1. CanSendMessage 信号量获取策略的根本差异

**分析描述**

| | 旧版 | 新版 |
|---|---|---|
| 获取策略 | `osWaitForever` 无限等待 | 10ms 超时 |
| Mailbox 预检 | 无 | 5ms 轮询检测 |
| 失败处理 | 未检查返回值，未释放信号量 | 失败时释放信号量 |

**源码对照**

旧版 `source code/dummy-ref-core-fw/Bsp/communication/interface_can.cpp`：
```cpp
void CanSendMessage(CAN_context* canCtx, uint8_t* txData, CAN_TxHeaderTypeDef* txHeader)
{
    osStatus semaphore_status;
    if (canCtx->handle->Instance == CAN1)
        semaphore_status = osSemaphoreAcquire(sem_can1_tx, osWaitForever);  // ← 无限等待
    else if (canCtx->handle->Instance == CAN2)
        semaphore_status = osSemaphoreAcquire(sem_can2_tx, osWaitForever);
    else
        return;

    if (semaphore_status == osOK)
        HAL_CAN_AddTxMessage(canCtx->handle, txHeader, txData, &canCtx->last_heartbeat_mailbox);
    // ← 未检查 HAL_CAN_AddTxMessage 返回值
    // ← 无论发送是否成功，信号量已消耗
}
```

新版 `firmware/ref_core_f405/Bsp/communication/interface_can.cpp`：
```cpp
void CanSendMessage(CAN_context* canCtx, uint8_t* txData, CAN_TxHeaderTypeDef* txHeader)
{
    // 加固#1：5ms 预检查
    uint32_t startTick = HAL_GetTick();
    while (HAL_CAN_GetTxMailboxesFreeLevel(canCtx->handle) == 0) {
        if (HAL_GetTick() - startTick > 5) return;  // ← 失败静默返回
    }

    // 加固#2：10ms 超时
    osStatus semaphore_status;
    if (canCtx->handle->Instance == CAN1)
        semaphore_status = osSemaphoreAcquire(sem_can1_tx, 10);
    else if (canCtx->handle->Instance == CAN2)
        semaphore_status = osSemaphoreAcquire(sem_can2_tx, 10);
    else
        return;

    if (semaphore_status == osOK) {
        HAL_StatusTypeDef ret = HAL_CAN_AddTxMessage(...);
        // 加固#3：失败时释放信号量
        if (ret != HAL_OK) {
            osSemaphoreRelease(sem_can1_tx);  // 或 CAN2
        }
    }
}
```

**验证结果：✅ 完全正确**

**补充说明**：
- 旧版"信号量已消耗但不释放"的问题确实存在——当 `HAL_CAN_AddTxMessage` 失败时，信号量已被 `osSemaphoreAcquire` 消耗，但 `tx_complete_callback` 不会触发，导致信号量泄漏。
- 新版"10ms 超时"确实会导致高频调用场景下大量静默失败。

### ✅ 2. !HOME 执行路径的根本差异

**分析描述**

| | 旧版 | 新版 |
|---|---|---|
| 返回时机 | 电机真实到位后返回 | 命令入队后立即返回 "ok" |
| 等待方式 | ASCII 线程内 `while(IsMoving())` 阻塞 | 实时环内异步，等待在 `osDelay(10)` 循环中 |
| 超时保护 | 无 | 30s 兜底超时 |

**源码对照**

旧版 `source code/dummy-ref-core-fw/Robot/instances/dummy_robot.cpp`：
```cpp
void DummyRobot::Homing()
{
    float lastSpeed = jointSpeed;
    SetJointSpeed(10);

    MoveJ(0, 0, 90, 0, 0, 0);      // 设置目标姿态
    MoveJoints(targetJoints);         // 立即下发 6 轴位置
    while (IsMoving())               // ← 阻塞等待（ASCII 线程内）
        osDelay(10);                 // ← 每 10ms 检查一次

    SetJointSpeed(lastSpeed);        // 恢复速度后才返回
}
```

新版 `firmware/ref_core_f405/Robot/instances/dummy_robot.cpp`：
```cpp
void DummyRobot::Homing()
{
    float lastSlider = jointSpeedRps / SLIDER_TO_RPS;
    SetJointSpeed(10);

    MoveJ(0, 0, 90, 0, 0, 0, 0, 10);
    MoveJoints(targetJoints);
    // 新增 30s 兜底超时
    uint32_t _home_t0 = HAL_GetTick();
    while (IsMoving()) {
        if (HAL_GetTick() - _home_t0 > 30000U)
            break;                   // ← 超时退出
        osDelay(10);
    }

    if (IsMoving()) {                // ← 超时调试输出
        printf("[HOME TIMEOUT] jointsStateFlag=0x%02X (expected 0x7E)\n", ...);
        ...
    }

    SetJointSpeed(lastSlider);
}
```

**验证结果：✅ 完全正确**

**补充说明**：
- 旧版 `MoveJoints` 同步下发 6 轴后，ASCII 线程阻塞等待电机到位，整个过程在 ASCII 命令 handler 中完成。
- 新版 `MoveJoints` 仅设置 `targetJoints`，实际下发由实时环异步执行。命令 handler 立即进入 `while(IsMoving())` 循环等待。
- 新版增加了 30s 超时兜底和调试输出，避免"永久挂死"——这是对旧版缺陷的修复尝试，但引入了新的时序问题。

### ✅ 3. 实时环 50Hz 下发 + 信号量竞争

**分析描述**

| | 旧版 | 新版 |
|---|---|---|
| 下发频率 | 每 tick（5kHz）全量下发 | 每 100 tick（50Hz）下发 |
| 查询频率 | 无显式轮询 | 每 50 tick（100Hz）轮询 1 轴 |
| 地轨处理 | 无 | 新增 `SetPositionWithMotorRps` |

**源码对照**

旧版 `source code/dummy-ref-core-fw/UserApp/main.cpp`：
```cpp
void ThreadControlLoopFixUpdate(void* argument)
{
    for (;;) {
        ulTaskNotifyTake(pdTRUE, portMAX_DELAY);

        if (dummy.IsEnabled()) {
            switch (dummy.commandMode) {
                case DummyRobot::COMMAND_TARGET_POINT_SEQUENTIAL:
                case DummyRobot::COMMAND_TARGET_POINT_INTERRUPTABLE:
                case DummyRobot::COMMAND_CONTINUES_TRAJECTORY:
                    dummy.MoveJoints(dummy.targetJoints);  // ← 每 tick 下发
                    dummy.UpdateJointPose6D();
                    break;
                ...
            }
        } else {
            dummy.UpdateJointAngles();  // ← 每 tick 全量查询
            dummy.UpdateJointPose6D();
        }
    }
}
```

新版 `firmware/ref_core_f405/UserApp/main.cpp`：
```cpp
void ThreadControlLoopFixUpdate(void* argument)
{
    for (;;) {
        g_realtime_tick++;
        static uint32_t updateCounter = 0;

        ulTaskNotifyTake(pdTRUE, portMAX_DELAY);

        if (dummy.IsEnabled()) {
            switch (dummy.commandMode) {
                case DummyRobot::COMMAND_TARGET_POINT_SEQUENTIAL:
                case DummyRobot::COMMAND_TARGET_POINT_INTERRUPTABLE:
                case DummyRobot::COMMAND_CONTINUES_TRAJECTORY:
                    // 50Hz 下发（总线节流）
                    if (updateCounter % 100 == 0) {
                        dummy.MoveJoints(dummy.targetJoints);
                        // [v3.1] J7/地轨
                        dummy.motorJ[7]->SetPositionWithMotorRps(...);
                    }
                    // 100Hz 轮询 1 轴（约 14Hz/电机）
                    if (updateCounter % 50 == 25) {
                        dummy.UpdateJointAngles();
                    }
                    dummy.UpdateJointPose6D();
                    break;
                ...
            }
        }
        updateCounter++;
    }
}
```

**验证结果：✅ 完全正确**

**补充说明**：
- 旧版实时环每 tick（200μs）调用 `MoveJoints`，直接下发 6 轴 `SetAngleWithVelocityLimit`。
- 新版引入 50Hz 节流后，`MoveJoints` 每 100 tick（20ms）才调用一次，大幅降低了总线负载。
- 但查询频率从"每 tick 全量查询"降为"每 50 tick 查询 1 轴"，每轴查询频率约 14Hz（旧版每轴约 5kHz）。
- 信号量竞争分析准确：实时环 5kHz × 7帧/50Hz = 490帧/秒 × 100μs ≈ 49ms/s 占 CPU，实时环持锁时间约 1ms/次。

### ✅ 4. SetEnable / UpdateAngle 用 ALL 代理

**分析描述**

| | 旧版 | 新版 |
|---|---|---|
| SetEnable | `motorJ[ALL]->SetEnable(true)` 单帧广播 | 相同，`motorJ[ALL]->SetEnable(true)` 单帧广播 |
| 状态同步 | `state = FINISH`（enable 时立即同步） | `state` 不同步，等待 0x23 回包自动纠正 |
| 配套查询 | 无显式配套 UpdateAngle | enable 后调用 `motorJ[ALL]->UpdateAngle()` |

**源码对照**

旧版 `source code/dummy-ref-core-fw/Robot/actuators/ctrl_step/ctrl_step.cpp`：
```cpp
void CtrlStepMotor::SetEnable(bool _enable)
{
    state = _enable ? FINISH : STOP;  // ← enable 时立即同步 state

    uint8_t mode = 0x01;
    txHeader.StdId = nodeID << 7 | mode;
    ...
```

旧版 `source code/dummy-ref-core-fw/Robot/instances/dummy_robot.cpp`：

新版 `firmware/ref_core_f405/Robot/actuators/ctrl_step/ctrl_step.cpp`：
```cpp
void CtrlStepMotor::SetEnable(bool _enable)
{
    // [F1 修复] enable 时不再同步 state=FINISH
```

```cpp
void DummyRobot::SetEnable(bool _enable)
{
    ...
    motorJ[ALL]->SetEnable(_enable);  // ALL 代理广播
    hand->SetEnable(_enable);
    isEnabled = _enable;
```

**验证结果：✅ 完全正确**

**补充说明**：
- 旧版 `SetEnable(true)` 时 `state = FINISH`，使 `IsMoving()` 返回 false，即使电机实际在运动。
- 新版 `SetEnable` 不再同步 state，等待 CAN 0x23 回包自动纠正。
- 新版增加 `motorJ[ALL]->UpdateAngle()` 配套，这是对旧版缺陷的修复尝试，但引入了 ALL 帧失败风险。
- 分析中提到的"如果这 3 帧中任何一帧因信号量超时失败"的问题确实存在，但这是新引入的"加固"逻辑本身的脆弱性。

### ✅ 5. UpdateJointAngles 从全量查询改为轮询

**分析描述**

| | 旧版 | 新版 |
|---|---|---|
| 查询方式 | `motorJ[ALL]->UpdateAngle()` 单帧触发 7 电机 | 单播轮询，每次只查 1 轴 |
| 查询频率 | 每 tick 全量查询（5kHz/轴） | 7 轴轮询一遍约 14ms（71Hz/轴） |
| SetEnable 配套 | 无 | 额外调用一次 ALL 查询 |

**源码对照**

旧版 `source code/dummy-ref-core-fw/Robot/instances/dummy_robot.cpp`：
```cpp
void DummyRobot::UpdateJointAngles()
{
    motorJ[ALL]->UpdateAngle();  // ← 单帧触发全部电机
}
```

新版 `firmware/ref_core_f405/Robot/instances/dummy_robot.cpp`：
```cpp
void DummyRobot::UpdateJointAngles()
{
    static int currentIndex = 1;  // 轮询索引，1~7（J1~J7）
    
    motorJ[currentIndex]->UpdateAngle();  // ← 单播，每次 1 轴
    currentIndex++;
    if (currentIndex > 7) currentIndex = 1;  // J1~J7 循环
}
```

**验证结果：✅ 完全正确**

**补充说明**：
- 旧版 ALL 查询每 tick（200μs）触发一次，每轴刷新率 5kHz。
- 新版轮询方案：
  - 实时环每 50 tick（10ms）调用一次 `UpdateJointAngles()`
  - 每次只查 1 轴，7 轴轮询一遍需要 70ms
  - 每轴查询频率约 **14Hz**
- 旧版 ALL 查询每 tick 触发 7 个电机同时回包（7 个 CAN 0x23），可能造成总线瞬时拥塞。
- 新版轮询解决了总线拥塞，但牺牲了刷新率。分析中"SetEnable 后 ALL 帧失败无补偿"的问题确实存在。

## 根因链条总结

```
信号量 10ms 超时 (分析1)
    ↓ 某些帧静默丢弃
SetEnable / UpdateAngle 的 ALL 帧丢失 (分析4)
    ↓ jointsStateFlag 无法更新（没有 0x23 回包）
IsMoving() 永远返回 true (jointsStateFlag != 0x7E)
    ↓ Homing()/Resting() 阻塞在 while(IsMoving())
命令 handler 永久挂死 (分析2)
    ↓ g_cmd_in=2, g_cmd_out=1
ASCII 线程"死循环"现象 (实测现象)
```

**关键脆弱点**：

1. **CanSendMessage 10ms 超时静默失败**：调用方完全不知道发送失败，没有任何重试机制。
2. **ALL 帧一次性发送无补偿**：SetEnable + UpdateAngle 依赖 3 帧 ALL 帧全部成功，失败即导致 jointsStateFlag 永远无法更新。
3. **查询频率从 5kHz 降至 14Hz**：轮询方案降低了总线负载，但大幅延长了状态同步延迟。

---

## 修正建议

1. **CanSendMessage 失败需要显式通知调用方**，或增加重试机制。
2. **ALL 帧需要重试逻辑**：SetEnable + UpdateAngle 的 ALL 帧失败时应重试 N 次。
3. **增加查询频率**：轮询间隔从 50 tick 缩短到 10 tick，使每轴查询频率达到 71Hz。
4. **保留旧版全量查询作为备选**：当总线空闲时可用 ALL 查询，高负载时降级为轮询。
