# START使能调度优化（2026-10-16）

用户授权先实施方案1：只提高普通START启动阶段的发送机会，不缓存保护配置，不省略检查或确认。本轮不操作串口/ST-Link、不烧录、发送运动或提交。统一固件构建与同时进行的CBENCH剖析工作协调，避免覆盖同名产物。

## 改动与保留的约束

主控 `firmware_new/dummy-ref-core-fw/Robot/instances/protection_coordinator.cpp` 仅改三处调度：

- `START_QUERY`、`START_VERIFY` 可以使用每个5ms控制轮询剩余的发送机会，查询间隔由20ms改为5ms；共用分支里的`CAL_QUERY`保留原发送槽和20ms间隔。
- `PROFILE`仅在`startAfterProfile`时开放每轮剩余发送机会。收到匹配ACK后原代码会把`lastSend`回拨25ms，因此下一个配置步骤可在5ms轮询推进。
- `PollProfile`原有20ms未确认重试间隔保持；收到错误、旧事务、错误节点或参数的回报不能据此推进。不是每5ms重发所有未确认配置。

`Send`仍检查`txUsed`和运动epoch，协调器这一轮最多提交一帧。前置STOP预算、lease、取消旧任务和事件ACK仍先于普通START。CAL、保护退避、参数设置等其他任务不扩大可发送槽，不改主控/电机控制频率或任务优先级。

每次START仍执行新鲜8节点查询、7轴各BEGIN/下限/上限/方向/COMMIT、再次8节点验证，最后才进入实际使能流程。没有配置缓存、跳过保护或使用旧位置提前报告成功。电机配置COMMIT为RAM事务，并非每次保存EEPROM。

`dummy_robot.cpp::PollSoftStop`的最终token查询、ENABLE_HOLD及确认维持原10ms发送节奏。电机可能先回复处理前的phase，主控仍要求正确token、NORMAL及有效位置；不会把首次收到命令当使能完成。上位机及old助手的START命令/回执语义保持，没有新界面或协议。

## 时间解释

旧调度正常无重试时，协调器两轮8节点查询加7轴35次配置约1秒，最后使能确认和通知另计。方案1先把健康情况下的新步骤推进压到5ms粒度；实际时间仍受CAN忙、回执延迟、缺节点、RTOS和输出通知影响，不能把离线结果当设备最坏时间。

真实生产协调器C++新旧回放：无丢包时至外部`RequestStart`边界1015→265ms；35ms回包延迟1765→1375ms，CAN忙100ms为1115→365ms。测试外部robot接口为stub，以上均不包含最终电机使能确认，不能称整个实物START只需265ms。预计完整正常使能可先以约0.4～0.6秒为目标，实机待验收。

START优先使用剩余预算；缺节点导致持续查询时，末尾低优先级只读CAN诊断可能延后或显式超时。前置安全流量仍优先。若后续需要优化诊断公平性，另行讨论，不扩展本轮调度范围。
