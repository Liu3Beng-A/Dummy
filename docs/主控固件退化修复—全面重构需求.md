## 1. 背景

### 1.1 发生了什么

2026-08 月的 v2.7/v2.8 重构在主控固件中引入了多项退化（degradation）：

- **新增功能**：堵转协议 v3、7轴同步抵达、加速度同步查询、力矩模式、SERVO_J、RGB灯效扩展——**这些全部保留**
- **退化功能**：某些旧版行为在重构中被意外改变或删除，导致用户习惯的体验下降

### 1.2 用户报告的症状

| 症状 | 严重度 |
|------|--------|
| OLED 上 `*` / `_` 关节运动标记不更新 | **P0** |
| 上电显示的模式和之前不一样 | **P0** |
| `!DISABLE` 后进入死循环 | **P0** |
| `!STOP` 在 `!HOME` 中途发无效 | **P0** |
| OLED 卡顿 / 旧版丝滑 | **P1** |
| 指令静默丢弃（显示 ok 但电机不动）| **P0** |
| 发指令后 RGB/OLED 卡死（根因：CAN ISR 里 printf） | **P0** |

### 1.3 退化原因速查

| 根因 | 后果 |
|------|------|
| `UpdateJointAnglesCallback` 不再写 `jointsStateFlag` | OLED `*`/`_` 永远不变 |
| `IsMoving()` 从 `jointsStateFlag` 改成位置误差判定 | `!DISABLE` 后死循环，`!STOP` 无效 |
| `DEFAULT_COMMAND_MODE` 从 `INTERRUPTABLE` 改成 `SEQUENTIAL` | 上电默认模式变了 |
| CAN ISR 里调用 `printf` | 主控线程饿死，RGB/OLED 卡死 |
| `UpdateJointAngles()` 改为 4 组轮询 + 节流 | 关节角度更新滞后，OLED 卡顿 |
| `osDelay(20)` 硬节流 OLED | OLED 帧率从 60fps 降到 50fps |
| `SetStallMode()` 从 ISR 调 `ClearFifo()` | 指令队列被破坏 |

### A1：OLED `*`/`_` 关节标记永远不变

**问题（大白话）**

OLED 屏幕底部有一排 `_` 或 `*` 标记，表示每个关节是静止还是运动中。旧版会实时更新，新版永远是 `______`（6 个下划线），动或不动都一样。

**根因**

`UpdateJointAnglesCallback()` 函数（`dummy_robot.cpp` line 454-462）只更新 `currentJoints`，不更新 `jointsStateFlag`。

**固件核查**（确认存在）：
```cpp
// dummy_robot.cpp line 454-462
void DummyRobot::UpdateJointAnglesCallback()
{
    for (int i = 1; i <= 6; i++) {
        currentJoints.a[i - 1] = motorJ[i]->angle + initPose.a[i - 1];
        // ⚠️ 旧版这里有 jointsStateFlag 位运算，新版完全删除了
    }
    currentRailPos = motorJ[0]->angle / 360.0f * 5.0f;
}
```

**解决方案**：在 `UpdateJointAnglesCallback()` 恢复位运算逻辑：

```cpp
void DummyRobot::UpdateJointAnglesCallback()
{
    for (int i = 1; i <= 6; i++) {
        currentJoints.a[i - 1] = motorJ[i]->angle + initPose.a[i - 1];
        // 恢复：更新到位标志
        if (motorJ[i]->state == CtrlStepMotor::FINISH)
            jointsStateFlag |= (1 << i);     // ← FINISH 置 1（bit=1 表示到位）
        else
            jointsStateFlag &= ~(1 << i);    // ← 非 FINISH 清 0
    }
    currentRailPos = motorJ[0]->angle / 360.0f * 5.0f;
}
```

> ⚠️ **方向陷阱**：直觉上容易写成 `FINISH→&=` `非FINISH→|=`（即"FINISH 清 0"），**那是错的**。
> 旧版实际是 `FINISH→|=` `非FINISH→&=`（即"FINISH 置 1"）。配合 A3 的 `!= 0b1111110` 才自洽——IsMoving 期望 flag 全 1 才算停。
>
> 上次修复（2026-09-04）正好写反了，bug 链路：
> - 实际代码：`FINISH→&=` `非FINISH→|=` → bit=1 表示"未到位"
> - IsMoving：`jointsStateFlag != 0` → 任何 bit=1 都算在动
> - 电机使能后第一个 0x23 回包：电机端 `STATE_STOP`、`isFinished=0` → 触发"非 FINISH"分支 → 所有 bit 置 1
> - 结果：IsMoving 永远 true，!HOME/!RESET 死循环，`>...` 全部被静默丢弃

**注意**：`motorJ[i]->state` 是 `CtrlStepMotor::FINISH/RUNNING/STOP`，在 `ctrl_step.cpp` 的 `UpdateAngleCallback` 中由 CAN 0x23 回包更新。

**改动范围**：`dummy_robot.cpp` line 454-462

### A2：上电默认模式保持 SEQUENTIAL（不动）

**用户决策**：保持 `SEQUENTIAL`，不动 `DEFAULT_COMMAND_MODE`。

**串口助手阻塞/非阻塞切换按钮核查结果**：

| 检查项 | 结果 |
|--------|------|
| 固件命令前缀 | `>` = 阻塞，`&` = 非阻塞 |
| 串口助手 `send_movej()` | 固定发 `>` 前缀 |
| 阻塞/非阻塞切换按钮 | **已存在**，但切换的是固件 `#CMDMODE` 模式，不是前缀 |

**实际工作原理**：

| 按钮状态 | 串口助手发送 | 固件行为 |
|---------|------------|---------|
| "阻塞(等ok)" | `#CMDMODE 1`（SEQUENTIAL）| `ParseCommand` 走 `while(IsMoving())` 等到位后返回 ok |
| "非阻塞" | `#CMDMODE 2`（INTERRUPTABLE）| 立即返回 ok，新命令可打断 |

**这个方案比切换 `>` vs `&` 前缀更好**：

| 对比 | 切换 `>` vs `&` 前缀 | 切换 `#CMDMODE`（当前方案）|
|------|---------------------|------------------------|
| 用户体验 | 按钮文字"阻塞/非阻塞"直观看不懂 | 按钮文字直接说"等 ok" vs "不等"，更直观 |
| 发送内容 | 每次都要变前缀 | 固定 `>`，不变 |
| UI 复杂度 | 要加新变量/逻辑 | 已有变量 `cmd_block_mode_var`，复用 |

**结论**：串口助手实现完全正确，无需改动。`send_movej()` 固定发 `>` 是正确的。

### A3：`!DISABLE` 后死循环（固件核查 + 重分析）

**问题（同上）**

发 `!DISABLE` 后程序卡在等待电机停止的循环里。

**根因（同上）**：`IsMoving()` 用纯位置误差，`MoveJ` 后 `targetAngle = currentAngle`，立刻 false。

**固件核查结果**（`dummy_robot.cpp` line 679-693）：

```cpp
bool DummyRobot::IsMoving() {
    static constexpr float EPSILON_DEG = 1.0f;
    static constexpr float EPSILON_MM  = 0.5f;

    if (fabsf(currentRailPos - targetRailPos) > EPSILON_MM)
        return true;

    for (int i = 1; i <= 6; i++) {
        if (fabsf(motorJ[i]->angle - motorJ[i]->targetAngle) > EPSILON_DEG)
            return true;
    }
    return false;
}
```

**Bug 路径**（`MoveJ` line 367-370）：
```cpp
// 写入目标角度（纯位置误差判定用）
for (int j = 1; j <= 6; j++) {
    motorJ[j]->targetAngle = targetJointsTmp.a[j - 1] - initPose.a[j - 1];
}
```

`MoveJ` 末尾立刻把 `targetAngle` 设为新目标，`MoveJoints` 把指令下发给电机，但 `IsMoving()` 检查 `|angle - targetAngle|` 时，两者几乎相等（因为电机还没开始动），立刻返回 false。

**电机 state 字段（`CtrlStepMotor::state`）完全未使用**：
- `UpdateAngleCallback` 接收 `isFinished` 并写 `motorJ[i]->state`（在 `ctrl_step.cpp` 中）
- 但 `IsMoving()` 从不读这个字段
- 电机端 `state == FINISH` 表示真实到位，但主控完全不看

**解决方案（两条路，选一）**：

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **方案甲** | `IsMoving()` 改回 `jointsStateFlag != 0b1111110` | 等电机端真实 FINISH，语义正确 | 需要 0x23 回包可靠 |
| **方案乙** | `IsMoving()` 同时检查 `state == RUNNING` | 只需加一个字段比较，干净 | `state` 需要可靠回包 |

**推荐方案甲（已确认）**：恢复 `jointsStateFlag` 写入（A1 修复后），`IsMoving()` 改为 `jointsStateFlag != 0b1111110`，等电机端真实 FINISH 状态。

> ⚠️ **方案甲的隐藏前置条件**（上次修复漏掉的关键点）：
>
> `IsMoving()` 用 `jointsStateFlag` 判定有个固有问题——**flag 的初始状态不可控**：
> - 系统上电时 `jointsStateFlag = 0b0000000`（`dummy_robot.h:267`），但电机使能后第一个 0x23 回包电机端是 `STATE_STOP`、`isFinished=0`，按 A1 逻辑会被置 1，导致 IsMoving 永远 true
> - **解决办法**：必须保留旧版 `MoveJ`/`ServoJ` 末尾的 `jointsStateFlag = 0;` 复位动作（参见 §4 A3 配套的关键行）
> - 这一行在 §4 "A3 配套" 清单里原本漏写，**必须补上**，否则 A1+A3 改完后仍是同样症状（!HOME 死循环、`>...` 被静默丢弃）
>
> ⚠️ **方向陷阱**（上次修复写错的根因）：
> A1 的代码示例方向是对的（FINISH→置 1），但**写代码时 `|=` 和 `&=` 极易看反**。请按下面这个"反直觉对照表"逐字符对照：
>
> | 字段语义 | 旧版实际 | 文档 A1 示例 | 上次实际改错 |
> |---|---|---|---|
> | `state == FINISH`（到位） | `jointsStateFlag \|= (1 << i)` | `\|=` ✅ | `&=` ❌ |
> | `state != FINISH`（运动/STOP）| `jointsStateFlag &= ~(1 << i)` | `&=` ✅ | `\|=` ❌ |
>
> 直观记忆：**bit=1 表示"已 FINISH 到位"**（IsMoving 期望全 1 才算停）。

**用户决策**：确认用方案甲。

> `IsMoving_重设计分析.md` 已删除，以上是重新基于固件核查的分析结果。方案甲最接近旧版行为。

**改动范围**：
- `dummy_robot.cpp` `IsMoving()`：改回 `return jointsStateFlag != 0b1111110;`
- `dummy_robot.cpp` `MoveJ`/`ServoJ` 末尾：**保留** `jointsStateFlag = 0;`（旧版逻辑）
- A1 修复（回调里写 flag）方向必须按上面对照表

### A4：`!STOP` 在 `!HOME` 中无效（与 A3 同根）

**问题（同上）**：`!STOP` 在 `!HOME` 运动中途发无效。

**根因**：与 A3 是同一个 Bug。`EmergencyStop()` 把 `targetAngle` 设为 `currentAngle`，`IsMoving()` 立刻 false。

**固件核查**（`dummy_robot.cpp` `EmergencyStop()` line 739-755）：
```cpp
void DummyRobot::CommandHandler::EmergencyStop() {
    context->MoveJ(context->currentJoints.a[0], ...);  // ← 设 targetAngle = angle，误差归零
    context->MoveJoints(context->targetJoints);
    context->motorJ[0]->SetPositionWithMotorRps(...);
    context->isEnabled = false;
    ClearFifo();
}
```

配合 A3 修复（`IsMoving()` 改回等电机真实 FINISH），`!STOP` 的急停路径也需要修复：
- 当前走 `MoveJ(target=current)` → 有 A3 Bug
- 应走 CAN 0x89 广播急停帧（电机端已实现制动，目前主控从未发过）

**A3 修复后自动解决的**：当 `IsMoving()` 等电机 FINISH 后，`EmergencyStop()` 里的 `MoveJ` 虽然把 `targetAngle` 设为当前位置，`IsMoving()` 会等电机真实停止，但这样改 `targetAngle` 仍然不对（没有急停制动）。

**TODO.md BUG-4 推荐的修复**：发 CAN 0x89 广播急停帧，让电机端走真急停制动，同时轮询所有电机 `state != RUNNING` 再返回。

**改动范围**：
- A3 修复（`IsMoving()` 改回等 FINISH）
- `EmergencyStop()` 改为发 CAN 0x89 广播

### A6：CAN ISR 里 printf 导致系统卡死

**问题（同上）**：发指令后 RGB/OLED 卡死。

**根因（同上）**：`can_protocol.cpp` 多处在 ISR 里调 `printf`。

**固件核查**（`can_protocol.cpp` line 178-200, 312-327）：

ISR 里的 printf 分两类：
1. **0x5A / 0x5C printf**（致命）：`SetStallMode()` 在 ISR 里调 + printf 直接阻塞 UART 信号量
2. **0x28~0x2B PID printf**（较轻）：只在 `#GET_PID` 时触发，普通使用不触发

```cpp
// can_protocol.cpp line 187-198（0x5A 堵转广播）
case 0x5A: {
    uint8_t stallNodeId = data[0];
    uint8_t stallCmd = data[1];
    if (stallCmd == 1) {
        dummy.SetStallMode((int)stallNodeId);  // ← ISR 里调！含 ClearFifo()
        printf("[STALL] node=%d TRIGGER\r\n", stallNodeId);  // ← ISR 里 printf！
    } ...
}

// can_protocol.cpp line 198-208（0x5C 查询响应）
case 0x5C: {
    printf("[STALL_STATUS] node=%d en=%d\r\n", id, qval);  // ← ISR 里 printf！
}
```

`printf` → `_write` → `uart4StreamOutputPtr->process_bytes()` → `osSemaphoreAcquire(sem_uart4_dma, 10ms)`，在 UART DMA 忙时 ISR 等 10ms × N 次 → 主线程饿死。

**解决方案**：全部改为事件标志 + 主线程 poll 打印（已在文档 §4 描述）。

**改动范围**：`can_protocol.cpp` 约 30 行

### A7：堵转期间只放行控制指令，运动指令全部丢弃

**问题（大白话）**

触发堵转后，发送任何指令都消失（被队列丢掉）。串口助手显示"发送失败"。

**根因**

`SetStallMode()` 里调用了 `commandHandler.ClearFifo()`，从 ISR（CAN 0x5A 分支）被触发，非线程安全。

**用户需求（已明确，文档同步）**：堵转期间的行为：

| 指令类型 | 示例 | 堵转期间行为 |
|---------|------|------------|
| **控制指令（放行）** | `!START`、`!DISABLE`、`!STOP` | 正常执行（解除堵转 / 急停）|
| **运动指令（丢弃）** | `>...`、`&...`、`@...` | 丢弃，返回 "ok" |
| **其他指令（放行）** | `!HAND_*`、`!RGB_*`、`#GETJPOS` 等 | 正常执行 |

这是用户原始需求（来自堵转检测重构文档），当前 `ClearFifo()` 实现过于粗暴（全部清空），需要改为：只丢弃运动指令，控制指令和其他指令正常入队/执行。

**解决方案（精确丢弃 vs 粗暴清空）**

**当前实现（粗暴）**：
```cpp
// dummy_robot.cpp SetStallMode()
commandHandler.ClearFifo();  // ← 全部清空，过于粗暴
```

**新实现（精确）**：
在 `CommandHandler::ParseCommand()` 入口加运动指令丢弃逻辑（与 A5 修复共用同一套判断）：
```cpp
// ParseCommand() 入口
if (context->isStalled) {
    // 放行控制指令：!START, !DISABLE, !STOP
    if (strncmp(_cmd, "!START", 6) == 0 ||
        strncmp(_cmd, "!DISABLE", 8) == 0 ||
        strncmp(_cmd, "!STOP", 5) == 0) {
        // 正常执行
    }
    // 丢弃运动指令
```

### C1：OLED 帧率从 ~20Hz 恢复到 ~50Hz（删除一行代码）

**问题**：`main.cpp` 第 221 行 `osDelay(20)` 导致帧率降至约 20Hz。

**铁证：旧版与新版的 OLED 驱动 100% 完全相同**

通过对比 `E:\Dummy-code\source code\dummy-ref-core-fw\`（旧版）和当前 `firmware/ref_core_f405/`（新版），关键文件**字节级一致**：

| 文件 | 对比结果 |
|------|---------|
| `Bsp/utils/software_i2c/soft_i2c.c`（软件 I2C 驱动） | ✅ **IDENTICAL** |
| `3rdParty/u8g2/u8g2_stm32f4.c`（U8g2 STM32 桥接） | ✅ **IDENTICAL** |
| `3rdParty/u8g2/cpp/U8g2lib.hpp`（SSD1306 类） | ✅ **IDENTICAL** |
| `3rdParty/u8g2/u8x8_cad.c`（I2C 命令序列合并） | ✅ **IDENTICAL** |
| `3rdParty/u8g2/u8x8_d_ssd1306_128x64_noname.c`（绘制 tile） | ✅ **IDENTICAL** |

**唯一差异**：`main.cpp` 的 `ThreadOledUpdate` 函数体。新版多了两行：
- 第 142-146 行：IMU 节流 100Hz（不影响 OLED）
- 第 221 行：`osDelay(20)` ← **罪魁祸首**

旧版的 `ThreadOledUpdate` 完全没有 `osDelay`，靠 `oled.sendBuffer()` 的软件 I2C 自然耗时限速，实测 FPS ≈ 50Hz。

**为什么软件 I2C 能跑到 50Hz？**

虽然 `Delay_us(5)` 硬编码看似把时钟限制在 100kHz（理论传输 1024 字节需要 ~100ms），但实际传输时间取决于多个因素：

1. **U8g2 内部优化**：`ssd13xx_fast_i2c` 会合并相邻命令到同一 I2C transfer
2. **SSD1306 列地址自动递增**：128 字节数据流式写入，无需中间命令
3. **i2c_data_transfer 24 字节分块**（不是 32 字节），更细粒度的 transfer
4. **CPU 实际位时间 < 10μs**：`Delay_us(5)` 是 SysTick 粗略计时，加上 GPIO 操作指令 cycle，实际可能在 ~7μs/bit

实测帧时间 ≈ 20ms（即 ~50Hz），其中：
- 软件 I2C 传 1024 字节 ≈ 15-18ms
- RAM 绘制（printf/clearBuffer）≈ 1-2ms
- IMU 读取（10ms 节流）≈ 1ms

**解决方案**：删 `osDelay(20)`，靠软件 I2C 自然限速。预期帧率恢复到 **~50Hz**（与旧版一致）。

**改动范围**：`main.cpp` 第 221 行，删 `osDelay(20);`
