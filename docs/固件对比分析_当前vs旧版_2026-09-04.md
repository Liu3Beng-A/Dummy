## 三、核心 Bug 详解（按致命度排序）

### Bug #1（P0-致命）：CAN RX ISR 内调用 `printf`，阻塞 10ms × N 次

**位置**：`firmware/ref_core_f405/UserApp/protocols/can_protocol.cpp` 第 86~115、195~201、245~280、312~318、405~416 行

**现象**：0x5A（堵转广播）、0x5C（堵转状态查询）、0x28~0x2B（PID 查询）回包到达时，**ISR 内部调用 `printf()`**。

```cpp
case 0x5A:  // can_protocol.cpp:86
{
    if (stallCmd == 1) {
        dummy.SetStallMode((int)stallNodeId);
        printf("[STALL] node=%d TRIGGER\r\n", stallNodeId);  // ← ISR 里 printf！
    }
    ...
}
```

**为什么致命**：

1. **ISR 内 `osSemaphoreAcquire` 阻塞**：`printf` → `_write` → `uart4StreamOutputPtr->process_bytes()` → 内部 `osSemaphoreAcquire(sem_uart4_dma, 10ms)`。在 UART4 DMA 没空闲时，**ISR 会等 10ms**。
2. **CAN FIFO 溢出**：10ms 期间新 CAN 回包堆积（电机端 5kHz 回 0x23，1ms/帧），CAN RX FIFO 满后丢包。
3. **主线程饿死**：`ThreadControlLoopUpdate`（Normal 优先级）解析 ASCII 命令需要 UART/USB RX 任务配合，UART/USB 任务也被同一 UART4 DMA 信号量阻塞 → 多任务连锁等待。
4. **Heap 损坏**：`printf` → `vsnprintf` 需要 malloc，**FreeRTOS 的 heap_4 从 ISR 调 malloc 是非法的**（无锁保护）。

**触发路径（解释你的三个测试）**：

| 测试 | 触发条件 | 卡死原因 |
|------|---------|---------|
| 一   | `!START` 后电机回 0x01 ack → 无 printf 触发 → 不应卡死 | **但 CAN RX 持续在跑**，新代码里 `IsMoving()` 走位置误差，0x23 回包本身不 printf，但**累积 ISR 开销**导致后续命令线程调度延迟 |
| 二   | `!HOME` 触发电机运动 → 堵转广播 0x5A 触发 → printf 阻塞 10ms × N 次 | **直接命中 Bug #1** |
| 三   | 第一次 `MoveJ` 走完，电机可能轻微失步 → 0x5A 触发 → printf | **直接命中 Bug #1** |

**为什么旧版没事**：旧版 `can_protocol.cpp` 只有 50 行，只处理 0x23/0x25，**不在 ISR 里 printf**。

---

### Bug #2（P0-致命）：`IsMoving()` 从 CAN 状态判定改成位置误差判定

**位置**：`firmware/ref_core_f405/Robot/instances/dummy_robot.cpp:679-693`

**旧版**（正常工作）：
```cpp
bool DummyRobot::IsMoving()
{
    return jointsStateFlag != 0b1111110;  // 等待电机端 CAN 0x23 回 FINISH
}
```

**新版**（有 Bug）：
```cpp
bool DummyRobot::IsMoving()
{
    // 纯位置误差判定：|实测 - 目标| > 1° → 运动中
    if (fabsf(currentRailPos - targetRailPos) > EPSILON_MM) return true;
    for (int i = 1; i <= 6; i++) {
        if (fabsf(motorJ[i]->angle - motorJ[i]->targetAngle) > EPSILON_DEG)
            return true;
    }
    return false;
}
```

**为什么致命**：

1. **`while(IsMoving()) osDelay(10)` 立刻退出**：`MoveJ(0,0,90,...)` 后 `targetJoints = currentJoints`，`MoveJoints` 把 `targetAngle` 设成目标位置。但电机**还没开始动**，`angle` 仍等于上一帧 CAN 回包的位置（通常偏差 ≤ 1°）。`IsMoving()` **立刻返回 false**。
2. **`!HOME` / `!RESET` 变成 fire-and-forget**：函数返回 `osDelay(10)` 只跑 1~2 次就退出，但电机还要跑 5~10 秒。
3. **`!STOP` 失效**：在 `!HOME` 中途发 `!STOP`，`EmergencyStop()` 把 `targetAngle = currentAngle`，`IsMoving()` 立刻 false → 主控认为停下了 → 电机还在跑。

**为什么旧版没事**：旧版 `IsMoving` 读 `jointsStateFlag`，这个 flag 由 **CAN 0x23 回包** 中的 `isFinished` 位更新，等电机端真实到位才置 1 → 主循环必须等到电机物理完成。

---

### Bug #3（P0-致命）：SEQUENTIAL 模式下新增「运动中丢弃新指令」分支

**位置**：`firmware/ref_core_f405/Robot/instances/dummy_robot.cpp:825, 855`

**新增代码**：
```cpp
case COMMAND_TARGET_POINT_SEQUENTIAL:
    if (context->MoveJ(...)) {
        // [v2.8 修复] SEQUENTIAL 模式下，若电机还在转，丢弃新指令回 ok，
        // 保留"上一条做完再做下一条"的语义，但不阻塞 FIFO 消费线程。
        if (context->IsMoving() && context->IsEnabled())
        {
            Respond(*usbStreamOutputPtr,  "ok");
            Respond(*uart4StreamOutputPtr, "ok");
            break;   // ← 新指令被丢弃！
        }
        ...
    }
```

**为什么致命**：

1. 配合 Bug #2 的 `IsMoving` 位置误差判定 → `MoveJ` 后 `target=current`，**`IsMoving()` 立刻返回 false** → 这个 if 不进 → `MoveJoints` 正常下发。
2. **但用户连发第二条指令时**，第一条的电机还在物理跑（因为没有 wait），第二条进 `IsMoving()=true` 分支 → 返回 `"ok"` + 丢弃 → 用户以为指令被接受了，但实际电机收不到新目标。
3. **串口助手显示「发送失败」**（其实是显示「ok」，但电机没动），用户就认为是 bug。

**影响**：OLED 刷新变慢，数字/动画明显拖后腿。但这不是"卡死"的主因。

### Bug #5（P1）：主循环 `UpdateJointAngles()` 改为 4 组轮询 + 节流到 100Hz

**位置**：`firmware/ref_core_f405/UserApp/main.cpp:50-52, 73-74, 83-89`

**影响**：OLED 上关节角度显示滞后 50~100ms。不是"卡死"主因，但是体验退化。

### Bug #7（P2）：`UpdateJointAnglesCallback` 不再写 `jointsStateFlag`

**位置**：`firmware/ref_core_f405/Robot/instances/dummy_robot.cpp:454-462`

**旧版**：
```cpp
currentJoints.a[i-1] = motorJ[i]->angle + initPose.a[i-1];
if (motorJ[i]->state == CtrlStepMotor::FINISH)
    jointsStateFlag |= (1 << i);
else
    jointsStateFlag &= ~(1 << i);
```

**新版**：只写 `currentJoints`，`jointsStateFlag` 永远 = 0。配合 Bug #2 的 `IsMoving` 改造，这字段已无意义。但其他模块（OLED 显示 `*`/`_`）还在读它 → 永远显示 `______`。

### Bug #8（P2-隐性）：CAN RX 0x5A 处理里调 `dummy.SetStallMode()`，里面有 `commandHandler.ClearFifo()`

**位置**：`firmware/ref_core_f405/Robot/instances/dummy_robot.cpp:518-529`

```cpp
void DummyRobot::SetStallMode(int motorIndex)
{
    SetRGBMode(RGB::RED_HEARTBEAT);
    isStalled = true;
    targetJoints = currentJoints;
    for (int j = 1; j <= 6; j++) {
        motorJ[j]->targetAngle = currentJoints.a[j - 1] - initPose.a[j - 1];
    }
    targetRailPos = currentRailPos;
    commandHandler.ClearFifo();   // ← 清空 ASCII 指令队列
    (void)motorIndex;
}
```

**影响**：从 ISR 里调 `osMessageQueueReset()` 是非线程安全的，会破坏 FIFO 状态机。即使不卡死，**任何正在排队的指令全部被吞掉**。这也解释了你看到的「再发指令就显示发送失败」。

## 九、大白话解释：到底改了哪些东西（按改动类别）

> 下面把每个改动用「原来是这样 / 现在是这样 / 实际后果」三句话讲清楚。**不区分新老功能**，全部列出，方便你判断改动范围。

### 9.1 运动完成判定（`IsMoving()`）

| 维度 | 旧版 | 新版 | 后果 |
|------|------|------|------|
| **判断依据** | 读电机端 CAN 回包里的 `state` 字段，等电机端报告「FINISH」 | 算位置误差：`|目标角度 - 实测角度| > 1°` → 算运动中 | 旧版是真等电机到位；新版只要数字上接近就认为到位 |
| **`while(IsMoving())` 循环行为** | 电机物理到位后才退出 | `MoveJ` 后第一帧就退出（因为目标 = 当前位置，误差为 0） | `!HOME` 函数提前返回，但电机还在跑 |
| **`!STOP` 效果** | 等电机真实停下后才返回 "ok" | 把 `targetAngle = currentAngle`，`IsMoving()` 立刻 false，主循环提前结束 | 主控以为停了，实际电机还在减速 |

### 9.2 电机状态字段（state 枚举）

| 旧版 | 新版 | 含义 |
|------|------|------|
| `RUNNING` | `RUNNING` | 电机在运动 |
| `FINISH` | `FINISH` | 电机到位 |
| `STOP` | `STOP` | 电机失能 |
| （无）| `STALL` | **新增**：电机处于堵转 LOCKED 状态 |

### 9.3 关节状态标记（`jointsStateFlag`）

- **旧版**：CAN 0x23 回包时，`UpdateAngleCallback` 根据电机的 `isFinished` 位更新 `jointsStateFlag`，OLED 用这个 flag 显示 `*`（到位）或 `_`（运动中）。
- **新版**：CAN 0x23 回包时**只更新 `currentJoints`**，不再更新 `jointsStateFlag`。这个 flag 永远是 0。
- **后果**：OLED 上的 `*` / `_` 永远不变化，永远显示 `______`。

### 9.5 OLED 显示任务（`ThreadOledUpdate`）

### 9.14 堵转处理（`SetStallMode()`）

- **旧版不存在**（电机端也没堵转广播）。
- **新版新增**：从 CAN ISR 进来 → 切 RGB 红色心跳 → 设 `isStalled = true` → 同步 `targetJoints = currentJoints` → **`ClearFifo()` 立即清指令队列**。
- **问题**：`ClearFifo()` 从 ISR 调是非线程安全的，且把排队指令全吞了。

### 9.15 RGB 灯效（`rgb.cpp/hpp`，**完全重写**）

### 9.16 EEPROM 配置（`EepromConfig` 结构）

- **影响**：上电后从 EEPROM 读灯效配置，配合新 RGB 系统使用。

### 9.17 7 轴速度规划（`ComputeSyncSpeeds`）

- **旧版**：用 `AbsMaxOf6` 找最大关节差，按 max 角度算时间，再按各关节距离比例分配速度。
- **新版**：70 行新算法 `ComputeSyncSpeeds`，按梯形曲线模型做 7 轴同步抵达规划，含迭代收敛。
- **影响**：运动更平滑，但旧版 `AbsMaxOf6` 没了（只取最大关节决定总时间，新版每关节都按梯形曲线算）。

### 9.18 速度单位变化

- **旧版**：slider 单位是「°/s」（degree per second），按关节角度算。
- **新版**：slider 单位是「电机轴 r/s」（rotations per second，按电机输出轴算）。
- **换算**：`r/s = °/s × reduction / 360`。
- **`SLIDER_TO_RPS = 0.30`**（slider 100 → 30 r/s）。
- **`AXIS_MAX_RPS[7] = {30,30,30,30,30,30,30}`**（各轴物理上限，旧版没有这个常量）。

### 9.19 加速度处理

- **旧版**：`SetJointAcceleration(_acc)` 范围 0~100，按 `_acc/100 * DEFAULT_JOINT_ACCELERATION_BASES.a[i-1]` 算，传给电机的「百分比」。
- **新版**：`SetJointAcceleration(_acc)` 范围 1~5000（r/s²），直接下发浮点 `r/s²`。`DEFAULT_JOINT_ACCELERATION = 150.0f`。
- **`Init()` 时新增 `SyncAllMotorAcceleration()`**：上电时给 8 个电机发 0x2C 查询，缓存到 `jointAccRuntime[]` 供后续算法使用。

### 9.20 同步查询机制（`#GETJACC` / `#GETI`）

- **旧版**：直接读固定字段（没有同步查询机制）。
- **新版**：缓存 + 时间戳模式：
  1. 记住旧时间戳 `old_ms`
  2. 发 CAN 0x2C / 0x2D 查询
  3. `osDelay(1)` 轮询新时间戳（最多 30ms）
  4. 时间戳变了就打印新值；没变就报 `timeout (CAN no echo)`
- **作用**：避免 ISR 里 printf 与 ASCII 任务的 UART TX 冲突（**但 ISR 里其他 printf 还在**）。
