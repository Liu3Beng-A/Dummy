### 测试流程：先保持检测启用

1. 关闭旧助手，运行更新后的根目录 `串口助手_old.py`，开启完整日志。供电保持已验证的10A输出限流设置。烧录后先用“整组版本查询”核对九板：均为 `.03`、上述批次/时间/摘要，板型按上表。手动查询则按 `#FW_VERSION 0` 到 `#FW_VERSION 8` 逐条发送；0是主控，不能只查0判断九板一致。
2. 建立可信坐标。按此前成功的流程，在J1～J6真实处于REST姿态 `{0,-75,180,0,0,0}` 时执行机械校准，等 `!CALIBRATION ok`。烧录重启后不能直接沿用旧RAM多圈原点，也不要在任意姿态把当前位置标成REST。地轨和夹爪校准应正常退让、复触和返回。
3. 仅RAM启用普通堵转检测，不SAVE、不恢复默认。逐条发送，上一条成功后再发下一条；ENABLE需等七轴确认，START需等成功回执：

```text
!DISABLE
#STALL_SET 0 ENABLE 1
!START
```

4. 从有实际位移的REST起点读取基线，每条等 `end`，然后执行HOME。运动中不连续轮询诊断：

```text
#CAN_DIAG 2
#CAN_DIAG 3
!HOME
```

5. 不论HOME成功或STOP，都尽快逐条读取下面完整记录。每条等 `end` 或明确错误再发下一条。若先报其他轴的错误，优先查该轴的CAN_DIAG与LAST，再补J2/J3。**STOP期间现在直接查MOTION，无需先DISABLE**；取证完成前不要START、失能、复位、重校准或改参数。

```text
#CAN_DIAG 2
#CAN_DIAG 3
#STALL_STATUS 2 LAST
#STALL_STATUS 3 LAST
#STALL_STATUS 2
#STALL_STATUS 3
#MOTION_STATUS
```

6. 若HOME成功，在运动完成后可额外发送 `!STOP`，等STOP确认，再发送精确 `#MOTION_STATUS`，验证助手确有TX且主控返回状态，随后才 `!DISABLE`。查询不要附加参数或后缀。若HOME已自行STOP，第5步已覆盖此检查。
7. 第一轮成功后，用此前成功的方式回到相同REST起点，启用检测再重复2～3次有实际位移的HOME。已经到HOME时再次零位移HOME不能证明负载运动正常。若再次失败，先保存第5步证据，暂停重复运动；把从连接、版本、校准、START到结束查询的完整日志发回，并注明实际运动/停机情况及任何断电复位时刻。

### 如何判断

- 功能通过：启用检测时真实HOME完成，未再出现 `PROTECTION_STATUS_TIMEOUT` / `COMMUNICATION_TIMEOUT`；STOP中MOTION查询产生TX并正常回包。
- 时序改善：同次启动的前后 `pollgap` 不再新增接近一秒的最大间隔，`m_at-up` 的差值增长不再接近一秒。两芯片起始计时有偏移，应比较同板前后差值，不要求绝对差等于零。
- `ctl_late`看前后增量；`rx_ovr`是累计位图，不是次数。若基线已有0x200且结束仍为0x200，不能声称本轮新溢出，也不能证明没有再溢出。
- `ctl_max`只量控制函数观测区域。移除其它ADC中断后，它仍可能接近原46μs，不能要求该值明显下降才算改善，也不能只凭它小于50μs认定完整CPU预算健康。
- 若仍为通信超时且LAST无触发记录，继续沿CAN接收/前台调度证据定位。若出现真实STALL及LAST快照，再依据电流、速度、误差和持续时间讨论阈值及回退。

### 查询与读数含义

```text
#CAN_DIAG 2
#CAN_DIAG 3
```

支持单个电机节点 1～8；此命令不支持节点 0。可选第二参数为请求号 1～65535，例如 `#CAN_DIAG 2 1001`。助手手动发送与按钮都会分配显式请求号；按钮“CAN诊断（参数节点）”读取电机参数页当前节点，选择 ALL 会拦截。STOP 或 CAL 锁定时仍可查询。每次等待同节点、同请求的 `end` 或明确错误再发送下一条；没有自动连续采样。

传输使用独立 selector 6，24 个 CAN word 带 CND1、schema、selector、板型与 DWT 标志；主控缓存乱序字段并验证完整 mask。文本含 43 个必需字段，助手完整校验后才生成 `CAN_SUMMARY`。旧固件会超时；旧 STALL/CAL 快照或部分行不能冒充完整诊断。原版本查询仍为 selector 7，STALL/CAL 查询含义不变。

| 字段 | 解释 |
|---|---|
| `query_rx`、`nonce_rx`、`last_rx` | 电机收到保护 QUERY 的次数、最后编号、HAL 毫秒时刻 |
| `probe_q`、`merge`、`full` | PROBE 新入队次数、合并次数、队满丢弃次数 |
| `txok`、`alst`、`terr`、`nonce_tx`、`last_tx` | 电机 PROBE 真实 TXOK、仲裁丢失、发送错误及最后成功编号/毫秒时刻；入邮箱不计为送达 |
| `age`、`tries` | 按原 100ms 年龄/16 次尝试预算丢弃的 PROBE 次数；这两个字段不是时间 |
| `depth`、`peak`、`head`、`head_age`、`flags` | 保护队列当前/历史峰值深度、队头命令及年龄；flags bit0=拥有邮箱、bit1=正在取消 |
| `rx_ovr` | RX FIFO 溢出错误累计位图：0x200=FIFO0，0x400=FIFO1；不是次数或丢帧数 |
| `m_q`、`m_txok`、`m_alst`、`m_terr`、`m_abort` | 主控对该节点 QUERY 的入邮箱、真实 TXOK、仲裁丢失、发送错误、取消次数 |
| `m_rx`、`m_match`、`m_reject` | 主控收到该节点 PROBE 的总数、按原规则匹配数、编号不匹配拒收数 |
| `m_sent`、`m_got`、`m_txn` | 主控当前已发请求编号、最后收到编号、最后真实 TXOK 的请求编号 |
| `m_at`、`m_rxage`、`m_pbage` | 主控快照真实 HAL 毫秒，以及任意保护帧/匹配探测回复的年龄 |
| `up`、`boot` | 电机 HAL 毫秒与原有启动命名空间；boot 不保证单调递增，不能独立当严格复位计数 |
| `cpu`、`dwt` | CPU Hz 与 DWT 可用标志；dwt=0 时零计时不代表健康 |
| `ctl_max`、`ctl_gap`、`pollgap`、`ctl_late` | 控制回调观测最大耗时、入口最大间隔、发送轮询最大间隔（前三者为 CPU 周期），以及耗时达到 50μs 预算或退出时 UPDATE 已置位的次数 |

计数在 RAM 中累积，不写 Flash、不提供清零命令；32 位计数可自然回绕。主控节点统计在恢复该节点默认值时可能重建，因此本测试不执行恢复参数。用同次启动的前后增量定位；计数并非故障瞬间自动冻结，而且运动结束到查询完成之间仍可能继续增长。电机 24 word 是同一快照；主控本地计数在开始打印时另取快照，两个芯片时刻没有同步，不能要求逐个请求的瞬时计数严格相等。

### 第二轮：RAM 关闭检测的相同位移对照（需要时）

第一轮取证完整后再失能、仅 RAM 执行 `#STALL_SET 0 ENABLE 0`，不 SAVE。坐标仍可信时，用此前成功方式回到相同 REST 起点；出现重新初始化证据时先重新建立坐标，不能直接用旧多圈位置继续。然后 START → 两节点 CAN_DIAG 基线 → HOME → 两节点 CAN_DIAG 结束快照。速度、供电、负载与位移尽量一致。不要在运动中频繁轮询诊断，避免额外流量干扰对照。

## 初次交付时的调查结论（保留历史）

不能认为“固件已经证明没有问题”。近期地轨日志中，MoveJ 的明确停机入口是 `PROTECTION_STATUS_TIMEOUT`：主控超过 1000ms 未得到匹配的保护状态探测回复，随后执行普通 STOP。该停机入口不会执行堵转回退。`LAST` 没有堵转记录也支持这一轮没有收到本地堵转事件，但不能据此证明实物没有阻挡。

09:04 校准中夹爪已完成 BACKOFF/RETOUCH/RETURN/DONE，随后地轨状态变为 IDLE/task0，并出现 BAD_TASK。用户确认发生在地轨物理限位处；运行上下文消失值得怀疑重新初始化，但没有启动原因寄存器证据，尚不能判定是供电、复位线、软件复位或其他原因。两份日志之间用户主动断电复位，不能跨日志拿运行计时证明异常重启。

本次版本功能先解决“板上究竟是哪份固件、是否九板同批”的证据缺口。它不提供 RCC 复位原因、启动次数或实时 ISR 耗时，也不修复以上停机问题。

## 版本查询

启动根目录 `串口助手_old.py`。连接后发送 `!DISABLE`，等主控确认失能，再点击查询区的“查询固件版本”。它逐条查询主控与 J1～J8，等待每板完整回复或超时，最后打印 `FW_SUMMARY`。

也可以逐条手动发送，等上一条 `end` 或明确错误后再查下一板：

```text
#FW_VERSION 0
#FW_VERSION 1
#FW_VERSION 2
#FW_VERSION 3
#FW_VERSION 4
#FW_VERSION 5
#FW_VERSION 6
#FW_VERSION 7
#FW_VERSION 8
```

**此命令的 0 专指主控，不是广播；其他指令原有 0=ALL 语义没有改变。** 手动版本查询只读，可在 STOP 或校准锁定期间使用。整组按钮要求已确认失能，并结束其他批量任务。

可选的第二个参数是十进制请求号 1～65535，例如 `#FW_VERSION 7 1234`。省略时主控自动分配。整组按钮显式提供请求号，按节点+请求号匹配，不把迟到回复、裸 `ok` 或部分回复当成成功。

每板有六行正式回复：

```text
FW_VERSION [7] req=1234 v=20261010.01 type=M57
FW_VERSION [7] req=1234 epoch=<UTC Unix秒>
FW_VERSION [7] req=1234 group=<16位十六进制批次>
FW_VERSION [7] req=1234 h0=<源码摘要前32位>
FW_VERSION [7] req=1234 h1=<源码摘要后32位>
FW_VERSION [7] req=1234 end
```

发布版本 `v`、UTC 时间 `epoch`、构建批次 `group`、拼接 `h0+h1` 的 SHA256 应在九板完全一致。类型应为主控 CORE、J7 M57、J8 GRIPPER；J1～J6 按实物选 M35/M42/M57，不能为了让类型相同而给不同型号刷同一个文件。

旧主控可能只返回裸 `ok`；旧电机不支持新 selector，会超时。助手会报告缺失或未匹配，不能据此认定整组已更新。版本查询显示的是固件内编译的身份，不等价于逐字节读回验证全部应用 Flash。

## 同一批构建的约束

五个目标共享同一发布版本、显式批次号、UTC 时间和生产输入摘要。摘要包含两个固件工程的生产目录、共享协议头、实际 CMake、链接脚本和主控 CMSIS 库，排除 build、文档和上位机文件。它不会把无关 Git HEAD 当成固件源码版本。

源码增删、链接脚本和实际库的依赖已登记。生产输入变化会重新配置身份；复用历史批次但改变源码、版本或时间会拒绝配置。每个 build 目录还记录编译工具和选项，历史约束依赖该目录中的登记文件，删除 build 也会删除其历史。因此以后每次交付都使用新批次号，并重新核对两工程和五产物。

## 烧录：保留校准与参数，不全片擦除

本次没有证据表明主控持久数据损坏，不需要为了排查而重写主控 EEPROM。主控的 RGB 持久设置和电机的编码器校准表、参数页应保留。全片擦除会丢失这些数据，且无法判定 STOP 的根因。

使用 ST-LINK Utility，对九块板分别执行以下步骤。烧录是用户执行的操作，本聊天没有操作设备。

1. 用本次交付目录内的文件，核对板卡型号与文件名。必要时先备份保留区；有读保护时不要解保护，解保护可能触发全片擦除。
2. 在 `Target → Erase Sectors` 中**只选择应用范围**。不选择全片擦除。
3. 用 `Program & Verify` 选择对应 **BIN**，起始地址显式填 `0x08000000`。应用区已经擦除后勾选 `Skip Flash erase` 和 `Verify after programming`。
4. 记录板号、文件、验证结果。全部九块板完成，再断开 ST-LINK，正常上电并通过 USB 查询整组版本。

| 板卡 | 文件 | 当前应用擦除范围 | 保留范围 |
|---|---|---|---|
| STM32F405 主控 | Core-STM32F4-fw.bin | sector 0～7，0x08000000～0x0807FFFF | RGB 位于 sector 11，不能擦 |
| J1～J6 | 按实物选 motor-35.bin / motor-42.bin / motor-57.bin | page 0～94，0x08000000～0x08017BFF | page 95～126 编码器表、page 127 参数 |
| J7 地轨 | motor-57.bin | 同上 | 同上 |
| J8 夹爪 | motor-gripper.bin | 同上 | 同上 |

电机保留区：编码器表 `0x08017C00～0x0801FBFF`；参数页 `0x0801FC00～0x0801FFFF`。链接脚本仍限定应用 95KiB，没有挪用这些保留区。

BIN 从起始地址连续定义所有字节，适合按清单精确长度读回后比较 SHA256。HEX 在向量表与 `.text` 间存在对齐空洞，不能把按 HEX 烧录后的整个范围直接与 BIN 的 SHA256 比较；既有 HEX 烧录应比较 HEX 记录覆盖的地址，或重新按上述 BIN 流程烧录。

只读核验可在 HotPlug 模式使用 `Compare device memory with file`，或从 `0x08000000` 按清单 BIN 长度保存读回文件再算摘要。不要把 `Program & Verify` 当作只读比对工具。
