# 发送就卡死 — 4 边界心跳定位方案（2026-09-16）

> **文档目的**：在 9-14 实测复盘和 9-16 收尾规划识别的 F1/F2/F3/F4/F4扩展 5 项修复**全部落地**后，问题仍然存在。
> 这意味着**之前识别的真凶方向并未打到点子上**，或者修复只解决了表象。需要换思路：**先用最小侵入的观测手段，定位卡死发生在哪个边界，再对症下药**。
>
> **本文档核心动作**：在 4 个边界各埋一个 `volatile` 心跳计数器，OLED 实时显示，肉眼直接判读卡死层级。

### 1.2 搜索范围需要扩展到哪里

之前所有修复都集中在 **CAN TX / SetEnable 路径**，但**未覆盖**以下可能的卡死点：

| 未覆盖点 | 怀疑程度 | 证据现状 |
|---|---|---|
| **UART4/USB 接收层**（DMA/中断未触发 / 队列满）| 中 | 9-14 文档未分析此层 |
| **ASCII 行缓冲累积**（缺 `\r`/`\n` 导致永远等行结束）| 低-中 | 串口助手发的是带 `\n` 的命令 |

| **命令队列 FIFO 满**（`commandHandler.Push` 返回 0）| 中 | ASCII 处理线程 `Pop(osWaitForever)` 阻塞 |
| **5kHz 实时环单次执行超时**（>200μs）抢占 ASCII | 中 | 未实测实时环执行耗时 |
| **FreeRTOS heap 耗尽**（隐式泄漏）| 中 | 未加水位监控 |
| **USB CDC TX 死锁**（与 UART4 互锁）| 低-中 | `interface_usb.cpp` 有 `tx_overrun_cnt++` 兜底，但无运行时暴露 |
| **OledTask / RGBTask 内部阻塞**（不是循环节流问题，而是内部调用的 API 阻塞）| 中 | 未分析 RGB 实现 / 软件 I2C |

### 1.3 核心思路

不修任何业务逻辑，**只在 4 个边界埋 4 个心跳计数器**，OLED 实时显示，肉眼判读卡死发生在哪一层。

- 投入最小：~50 行代码改动，1 次编译，1 次烧录
- 信息量最大：4 个边界各自卡死时表现不同，一眼可辨
- 风险最低：所有计数器都是 `volatile uint32_t` 原子读写，无副作用，可随时回滚

### 2.2 3 个"心跳探针"（验证调度层是否活着）

仅看 4 个 ASCII 边界不够 —— 如果系统**所有任务都被卡死**，4 个计数器也会全停。

增加 3 个任务级探针（每个任务的 `for(;;)` 循环入口 `++`）：

| 探针 | 任务 | 期望频率 | 含义 |
|---|---|---|---|
| `g_realtime_tick` | `ControlLoopFixUpdateTask` | 5000Hz | 5kHz 实时环是否被抢占 |
| `g_oled_tick` | `OledTask` | 60-80Hz | OLED 任务是否被饿死 |
| `g_rgb_tick` | `RGBTask` | 33Hz | RGB 任务是否被饿死 |

### 2.3 7 个计数器总览

| 计数器 | 位置 | 单位 | 增长速率（典型）|
|---|---|---|---|

## 三、判读规则（核心）

### 3.1 正常态（不卡死时）

| 计数器 | 增长速率 | 备注 |
|---|---|---|
| `g_byte_in` | 跟着 PC 发送速率涨 | 静默时停涨，正常 |
| `g_line_ready` | 等于 PC 发的命令数 | 静默时停涨 |
| `g_cmd_in` | = `g_line_ready` | 静默时停涨 |
| `g_cmd_out` | = `g_cmd_in` | 静默时停涨 |
| `g_realtime_tick` | **每秒 +5000**（5kHz）| 即使无命令也持续涨 |
| `g_oled_tick` | **每秒 +60-80**（帧率）| 即使无命令也持续涨 |
| `g_rgb_tick` | **每秒 +33** | 即使无命令也持续涨 |

### 3.2 卡死诊断矩阵

发 `!START` 命令后看 4 个 ASCII 计数器停在哪个位置（**3 个任务探针必须保持涨，否则是更严重的调度级卡死**）：

| 现象 | 结论 | 下一步定位 |
|---|---|---|
| `byte_in` 停 | **输入层卡死**（UART4 DMA/USB CDC RX 未触发）| 检查 `UartServerTask` 是否活着、`HAL_UART_Receive_DMA` 是否报错、`usb_rx_process_packet` 是否被调用 |
| `byte_in` 涨，`line_ready` 停 | **行缓冲累积卡死**（缺 `\r`/`\n`）| 检查 PC 端串口助手是否真的发了换行；检查 `parse_buffer_idx` 是否溢出 MAX_LINE_LENGTH |
| `line_ready` 涨，`cmd_in` 停 | **dispatch 卡死**（`ASCII_protocol_process_line` 未调 handler）| 检查 `response_channel.channelType` 识别分支是否异常 |
| `cmd_in` 涨，`cmd_out` 停 | **handler 卡死**（命令执行中卡住，最常见）| 加细颗粒：在 handler 内关键函数入口（`SetEnable` / `MoveJ` / `commandHandler.Push` / `Respond`）再埋计数器，定位是哪个分支卡死 |
| `cmd_out` 涨，**但 3 个任务探针之一停涨** | **调度层被饿死**（最严重）| 哪个任务停涨就是哪个任务被阻塞；可能是实时环执行超 200μs，或 ASCII 解析持锁时间太长 |
| 7 个全停涨 | **Watchdog 级别卡死**（中断都停了 / hardfault）| 检查堆栈溢出、hardfault handler、IWDG 是否触发 |

### 3.3 重点：cmd_in 涨 cmd_out 停 —— handler 卡死细定位

这是**最可能的卡死点**。`OnUsbAsciiCmd` / `OnUart4AsciiCmd` 内有几十个 `s.find` 分支，每个分支都调 `Respond()` 一次或多次。

如果 `!START` 走的是 `s == "!START"` → `dummy.SetEnable(true)` → `Respond("ok")` 路径，且卡死在此分支：

| 进一步诊断 | 计数器 |
|---|---|
| `dummy.SetEnable(true)` 之前 OK，之后停 | `SetEnable` 路径卡死（电机端未回包 / ALL 代理 CAN 帧未发出 / CAN 信号量异常）|
| `SetEnable` 返回后 `Respond` 之前停 | handler 函数体内某处隐式卡死 |
| `Respond("ok")` 调用后停 | **`Respond()` 写 UART4/USB 路径卡死** ← 9-14 文档未深入分析的层 |

**Respond 卡死的可能性**：
- `uart4_stream_output.process_bytes` 内 `osSemaphoreAcquire(sem_uart4_dma, PROTOCOL_SERVER_TIMEOUT_MS)` 超时（UART4 TX DMA 一直未完成）
- USB 路径 `osSemaphoreAcquire(sem_usb_tx, PROTOCOL_SERVER_TIMEOUT_MS)` 超时（USB TX 一直未完成）
- 串口助手 PC 端没在读 USB → USB CDC TX buffer 满 → 主控 TX 阻塞

### 4.4 改动 3：`ascii_protocol.cpp` 内 4 个 `++`

```cpp
// OnUsbAsciiCmd 入口:
void OnUsbAsciiCmd(const char* _cmd, size_t _len, StreamSink &_responseChannel)
{
    g_cmd_in++;  // [DIAG-2026-09-16] handler 入口
    // ... 原有逻辑 ...

    // 在 OnUsbAsciiCmd 函数末尾、所有 return 之前统一打:
    // （为简化，把 +1 放在单一出口；C++ 函数内多个 return 需要重构或加宏，
    //  此处选择最简方案：仅在函数体最末尾 +1，每个 return 前置一个
    //  `g_cmd_out++; return;` 行）
    g_cmd_out++;  // [DIAG-2026-09-16] handler 出口
}

// OnUart4AsciiCmd 同上
```

> **简化策略**：C++ 函数有多个 return 点，全部加 `g_cmd_out++` 麻烦。
> 用一个**RAII 风格的哨兵对象**：函数入口构造一个对象，析构时自动 `++g_cmd_out`。
> ```cpp
// ascii_protocol.cpp 顶部新增:
struct CmdExitGuard {
    ~CmdExitGuard() { g_cmd_out++; }
};
// 然后在每个 handler 入口:
void OnUsbAsciiCmd(...) {
    CmdExitGuard _guard;
    g_cmd_in++;
    // ... 函数体不变 ...
}  // _guard 析构 → g_cmd_out++
```
> 这样**任何 return 路径**（正常 return / 异常 / 早期 return）都会经过析构，零侵入。

| 风险 | 概率 | 影响 | 缓解 |
