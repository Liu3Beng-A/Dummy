# 步进电机固件全方位能力与机制分析报告

> 目标固件：dummy-42motor-fw（6 自由度机械臂底层步进电机驱动器）  
> 主控交互：CAN 总线，200Hz 下发 0x05 纯位置指令，痛点为堵转误判与高速静默失步。

---

## 执行摘要

| 维度 | 核心结论 |
|------|----------|
| **堵转与安全** | 堵转判据为「电流饱和 + 近零速度」持续 1 秒；触发后电机 **Sleep（释放力矩）**；**无主动 CAN 上报**，回传包无 state/ErrorCode。 |
| **运动与滤波** | 0x05 经 **PositionTracker 梯形规划** 生成软目标；0x14 加速度参与规划限速；DCE 误差被硬限幅，易在高速+限流下 **静默失步** 且无丢步检测。 |
| **遥测与完成** | 0x23 回传 `float 位置 + byte[4]=_isFinished`；**_isFinished 看的是 soft==goal 且 softVelocity==0**，与编码器真实到位、堵转无关。 |
| **隐藏能力** | DCE 为 **位置+速度复合环**（Kp/Kv/Ki/Kd）；0x03 电流模式经 **CurrentTracker 斜坡**，可做力矩透传；无“堵转/错误”主动上报。 |

## 维度 1：硬件级保护与堵转机制（Stall & Safety）

### 1.1 堵转判定逻辑

固件**不**使用编码器跟随误差、不使用反电动势，而是**电流 + 估计速度 + 持续时间**的复合判据。

**条件 1**：`stallProtectSwitch == true`  
- 主控通过 CAN **0x1B**（Set Enable Stall-Protect）或 EEPROM 中的 `enableStallProtect` 开启。

**条件 2**：电流满足其一  
- **电流模式**（MODE_COMMAND_CURRENT / MODE_PWM_CURRENT）：`current != 0`（有电流即参与判定）；  
- **其它模式**（位置/速度等）：`current == ratedCurrent`（**电流饱和**，即 DCE/PID 输出已被钳在限流值）。

**条件 3**：估计速度接近零  
- `abs(estVelocity) < MOTOR_ONE_CIRCLE_SUBDIVIDE_STEPS/5`（约 1/5 圈步进量，约 0.2 圈内的速度视为“静止”）。

**条件 4**：持续时间 ≥ 1 秒  
- `stalledTime` 每 50µs（CONTROL_PERIOD）累加，达到 `1000*1000`（微秒）即置位 `isStalled`。

```260:282:e:\Dummy-IDE\dummy\firmware\dummy-42motor-fw\Ctrl\Motor\motor.cpp
    // Stall detect
    if (controller->config->stallProtectSwitch)
    {
        if (// Current Mode
            ((controller->modeRunning == MODE_COMMAND_CURRENT ||
              controller->modeRunning == MODE_PWM_CURRENT) &&
             (current != 0))
            || // Other Mode
            current == config.motionParams.ratedCurrent)
        {
            if (abs(controller->estVelocity) < MOTOR_ONE_CIRCLE_SUBDIVIDE_STEPS / 5)
            {
                if (controller->stalledTime >= 1000 * 1000)
                    controller->isStalled = true;
                else
                    controller->stalledTime += motionPlanner.CONTROL_PERIOD;
            }
        } else // can ONLY clear stall flag  MANUALLY
        {
            controller->stalledTime = 0;
        }
    }
```

**结论**：本质是「**电流已顶满且编码器几乎不动**」持续 1 秒 → 判堵转。与主控端「指令角度 − 反馈角度」误差无直接关系，因此主控用大误差 alone 判堵转会与固件逻辑脱节。

---

### 1.2 保护动作（SetEnableStallProtect 置 true 且真实堵转时）

一旦 `isStalled == true`，在控制环**入口**即执行：

- `ClearIntegral()`：清空 PID/DCE 积分，防止积分饱和残留；  
- `focPosition = 0; focCurrent = 0`：输出置零；  
- `driver->Sleep()`：驱动进入 **Sleep**，**不锁轴、不刹车**，电机可被外力扳动。

```94:103:e:\Dummy-IDE\dummy\firmware\dummy-42motor-fw\Ctrl\Motor\motor.cpp
    if (controller->isStalled ||
        controller->softDisable ||
        !encoder->IsCalibrated())
    {
        controller->ClearIntegral();    // clear integrals
        controller->focPosition = 0;    // clear outputs
        controller->focCurrent = 0;
        driver->Sleep();
    }
```

状态机将 `controller->state` 设为 `STATE_STALL`，LED 等按堵转显示（如双闪）。  
堵转标志**仅能手动清除**（注释明确："can ONLY clear stall flag MANUALLY"）：主控侧可通过本地 **KEY2 单击** 触发 `ClearStallFlag()`，或若协议扩展则可由 CAN 命令清除。

---

### 1.3 报警上报：无主动上报，仅被动查询

- 固件**没有**在堵转（或 OVERLOAD/NO_CALIB）发生时**主动发送**任何 CAN 报文。  
- 所有回传均为**被动**：主控发 0x21/0x22/0x23/0x24/0x25 时，电机在 `OnCanCmd` 内组包并 `CAN_Send` 回复。  
- 回复中 **byte[4] 仅表示是否 `STATE_FINISH`**（1=完成，0=未完成），**没有** STATE_STALL / STATE_OVERLOAD / 错误码等字段。  

因此：**当前协议下，主控无法从任意一条现有 CAN 回传中直接读出「已堵转」**。要感知堵转只能：  
- 周期查询 0x23（或 0x21/0x22）并**结合自身启发式**（如长时间未 FINISH + 电流/位置推断），或  
- **扩展协议**：在回传中增加 state/ErrorCode，或新增 0x26 Get State（见破局建议）。

---

### 1.4 Overload 与 Stall 的区别

- **Overload**：非电流模式下 `current == ratedCurrent` 持续 1 秒即置 `overloadFlag`，`state = STATE_OVERLOAD`；**会随电流下降自动清除**。  
- **Stall**：同上电流+近零速度+1 秒，但 **不自动清除**，需手动 `ClearStallFlag()`。  
两者在现有回传中均**无**独立字节表示。

## 维度 2：运动控制与滤波机制（Motion & Control Loop）

### 2.1 0x05 位置模式真相：离散阶跃如何被处理

主控以 200Hz 发送 **0x05 Set Position SetPoint** 时：

1. **协议层**（`interface_can.cpp`）：  
   - 解析 `*(float*)RxData` 为目标位置（圈或单位×步进系数），乘 `MOTOR_ONE_CIRCLE_SUBDIVIDE_STEPS` 得 `goalPosition`（步进单位）；  
   - 若当前非 `MODE_COMMAND_POSITION` 则切换模式并恢复 `ratedVelocity = boardConfig.velocityLimit`；  
   - 调用 `SetPositionSetPoint(...)`，内部为 `goalPosition = _pos + encoderHomeOffset`。

2. **控制环侧**：  
   - 模式切换时 `softNewCurve = true`，下一拍会执行 `positionTracker.NewTask(estPosition, estVelocity)`，以**当前估计位置/速度**为起点；  
   - **每拍**（20kHz）调用 `positionTracker.CalcSoftGoal(goalPosition)`，得到 `go_location`、`go_velocity`（软目标位置与速度）；  
   - `softPosition = go_location`，`softVelocity = go_velocity`；  
   - 位置环使用 **DCE**：`CalcDceToOutput(softPosition, softVelocity)`，即跟踪的是**软目标**，不是裸的 `goalPosition`。

3. **PositionTracker 本质**：  
   - 内部按 `velocityUpAcc`/`velocityDownAcc`（由 0x14 设置的 `ratedVelocityAcc`）做**梯形加减速**积分；  
   - 限速为 `config->ratedVelocity`；  
   - 到达目标时减速到 0 并保持 `trackVelocity` 在 ±`speedLockingBrake` 内。  

因此：**主控的离散阶跃被固件内部的梯形规划器平滑成连续软目标**；相位滞后来自「软目标相对 goal 的跟踪延迟」+「DCE 对 soft 的跟踪延迟」，而不是一块独立的 LPF 系数 150。

---

### 2.2 主控设置 150.0 加速度（0x14）在底层如何参与

- **0x14** 写入：`tmpF = *(float*)RxData * MOTOR_ONE_CIRCLE_SUBDIVIDE_STEPS`，得到步进/秒² 的加速度；  
- 同时更新：  
  - `motor.config.motionParams.ratedVelocityAcc`  
  - `velocityTracker.SetVelocityAcc(...)`  
  - `positionTracker.SetVelocityAcc(...)`  
- 若 `_data[4]` 非 0，则置 `CONFIG_COMMIT` 写入 EEPROM。  

该加速度用于 **PositionTracker / VelocityTracker** 的加减速积分（`CalcVelocityIntegral`），即**限制的是软目标速度的变化率**；150 若为主控侧「圈/秒²」则固件会乘步进数得到内部加速度。

---

### 2.3 为什么会静默失步（物理转轴跟不上却“一切正常”）

- **无丢步/失步检测**：固件没有“编码器与指令偏差超过阈值即报错”的逻辑；控制环始终以 `estPosition`（编码器+估计前馈）为反馈，DCE 输出被钳在 `±ratedCurrent`。  
- **电流钳位**：当负载或惯性导致需要更大力矩时，DCE 输出饱和在 `ratedCurrent`，实际加速度受限；若指令变化过快（如 200Hz 大跨度 MoveL），软目标可能仍按 0x14 加速度平滑，但**实际电机加速度受电流限幅约束**，物理上会跟不上 → **静默失步**。  
- **DCE 误差限幅**：`pError` 被限制在 ±3200（约 1/16 圈），`vError` 被限制在 ±4000；大误差被裁掉后，环输出不会“爆表”，但**真实位置已落后**，系统仍按 `softPosition/estPosition` 判断 FINISH，**不会主动报错**。  
- **STATE_FINISH 只看软目标**：见维度 3，`softPosition == goalPosition && softVelocity == 0` 即 FINISH，与编码器是否真实到位无关，故失步后仍可能在一段时间后报 FINISH。

综合：**静默失步 = 电流/速度限幅 + 无“真实位置 vs 目标”的硬性检测**；固件不会主动打断主控控制流。

## 维度 3：CAN 遥测与状态同步（Telemetry & Feedback）

### 3.1 状态查询机制与 0x23 回传结构

- 回传**全部**由主控发起的 CAN 命令触发；电机**无**定时器驱动的周期上报。  
- 主控发一帧 → `HAL_CAN_RxFifo0MsgPendingCallback` 解析 `StdId` 得 `cmd`（低 7 位），调用 `OnCanCmd(cmd, RxData, DLC)`，在对应 `case` 里组包并 `CAN_Send`。

**0x23 Get Position 回传**：

| 字节 | 内容 |
|------|------|
| byte[0..3] | `motor.controller->GetPosition()` 的 float（圈或线性位置，取决于 `_isLap`，当前为默认 false，即多圈线性位置） |
| byte[4] | `motor.controller->state == Motor::STATE_FINISH ? 1 : 0`（即 _isFinished） |
| byte[5..7] | 未使用（DLC=8 时可为 0） |

回复 CAN ID：`(boardConfig.canNodeId << 7) | 0x23`。

---

### 3.2 _isFinished（完成标志位）的底层触发条件

状态更新在 `motor.cpp` 的 “Update State” 段：

- **位置模式**：`(softPosition == goalPosition) && (softVelocity == 0)` → `STATE_FINISH`，否则 `STATE_RUNNING`。  
- **速度模式**：`softVelocity == goalVelocity` → `STATE_FINISH`。  
- **电流模式**：`softCurrent == goalCurrent` → `STATE_FINISH`。  
- 其它（如 Trajectory/STEP_DIR）：当前实现直接设为 `STATE_FINISH`。  
- 若已堵转/过载/未校准：优先为 `STATE_STALL` / `STATE_OVERLOAD` / `STATE_NO_CALIB`，不会为 FINISH。

因此：**_isFinished 表示的是「内部软目标已等于指令目标且软速度为零」**，即规划器认为“本段运动已完成”，**不是**“编码器真实进入目标误差带”，也**不是**“指令队列空”。在存在静默失步时，软目标仍可能最终收敛到 goal，从而误报 FINISH。

**能否代替主控的“运动完成”判定**：  
- 可用于“规划层一段指令执行完毕”的粗判；  
- **不可**作为“机械臂末端已精确到位”或“无堵转/无失步”的可靠依据；若需可靠完成判定，建议配合 state/ErrorCode（见破局建议）和必要时主控侧误差带检测。

## 维度 4：隐藏的宝藏接口（Hidden Features）

### 4.1 闭环参数 DCE（SetDceKp / Kv / Ki / Kd）调节的是什么环

DCE 在 `CalcDceToOutput(_location, _speed)` 中使用：

- `pError = _location - estPosition`（位置误差，限幅 ±3200）；  
- `vError = (_speed - estVelocity) >> 7`（速度误差，限幅 ±4000）；  
- 输出 = (Kp×pError + Ki×∫(pError,kv×vError) + Kd×vError) >> 10，再钳到 ±ratedCurrent。

因此：**DCE 是位置环 + 速度前馈/阻尼的复合控制器**（P 对位置、I 对位置与速度误差的积分、D 对速度误差），输出为电流指令；**不是**纯速度环。Kp/Kv 调位置刚度与速度阻尼，Ki 消除静差，Kd 抑制速度误差。  
**对高速失步的帮助**：适当提高 Kp/Kv 可提高跟随刚度，但在电流已饱和时无法消除失步；根本仍在于限流、加速度与规划匹配（见破局建议）。

### 4.2 0x03 SetCurrentSetPoint（力矩/电流模式）真实表现

- **协议**：0x03 切到 `MODE_COMMAND_CURRENT`，`SetCurrentSetPoint((int32_t)(*(float*)RxData * 1000))`（单位 mA）。  
- **内部**：`goalCurrent` 被钳在 ±ratedCurrent；每拍 `currentTracker.CalcSoftGoal(goalCurrent)`，按 `ratedCurrentAcc`（默认 2×1000 mA/s）做**斜坡**，得到 `softCurrent`；控制环调用 `CalcCurrentToOutput(softCurrent)`，直接映射为 FOC 电流矢量。  
- **结论**：**支持电流/力矩设定**，但有**电流斜坡**，非瞬时阶跃；可用于力矩透传或柔顺控制，需注意斜坡时间与 ratedCurrentAcc。

## 破局建议（架构师结论）

### 问题 1：主控无法精准判断堵转

**建议**：  
1. **扩展回传（优先）**  
   - 在 0x23（或 0x21/0x22）回复中增加 1 字节 **state**：例如 0=STOP, 1=FINISH, 2=RUNNING, 3=OVERLOAD, 4=STALL, 5=NO_CALIB。  
   - 或新增 **0x26 Get State**，返回 state + 可选 ErrorCode。  
   - 主控周期查询（如 10–20 ms 一次），一旦 `state == STALL`（或 OVERLOAD）**立即停机并进入安全流程**，不再依赖「位置误差 + 阈值」单独判堵转。  
2. **可选：堵转时主动上报一帧**  
   - 在 `motor.cpp` 中当 `isStalled` 从 false 变为 true 时，组一帧「状态/错误」CAN 报文主动发送；主控监听该 ID 即可在堵转后 1–2 个周期内感知。  
3. **不推荐**：继续仅靠主控端「指令角度 − 反馈角度」阈值区分堵转与正常延迟——在现有强平滑与 1 秒堵转判定下，误判与漏判都难以避免。

### 问题 2：200Hz 盲发位置指令导致的高速失步

**建议**：  
1. **利用固件规划能力，降低有效指令率**  
   - 主控不要每 5ms 发一个“新目标”，可改为**发一个目标后等待 _isFinished 或超时**再发下一段；或做**主控侧轨迹分段**，每段只发一个 0x05，让固件内部梯形规划完成整段。  
2. **匹配加速度与限流**  
   - 0x14 设置的加速度不宜超过电机在 ratedCurrent 下能提供的实际加速度，否则必然出现“软目标跑得快、物理跟不上”；可结合 0x13 限速一起调。  
3. **可选：用 0x07 带速度限制的位置指令**  
   - 0x07 在设位置的同时限制本段最大速度，有利于在高速 MoveL 时约束单轴速度，减轻失步。  
4. **根本配合**  
   - 固件侧无法在不改协议的情况下“主动报失步”；若需可观测性，仍需**扩展 state/ErrorCode 或新增 0x26**，并视需求在固件中增加“编码器与目标偏差超阈值”的检测（需定义阈值与行为）。
