> 目标：主控 STM32F405 同 CAN 总线 200Hz 0x05 控制 6 轴（底座/大臂 42、腕部/末端 35）时，统一驱动逻辑的可行性与避坑要点。

## 执行摘要

| 维度 | 结论 |
|------|------|
| **堵转保护** | 35 与 42 **逻辑完全一致**：SetEnableStallProtect(0x1B)、触发条件（电流饱和 + 近零速度 + 1 秒）、保护动作（Sleep）相同；**无**针对 35 小电机的更敏感失步判定。 |

## 维度 1：堵转检测与保护机制的异同（Stall Protection）

### 1.1 35 固件是否实现 SetEnableStallProtect

**结论：与 42 完全一致。**

- **0x1B** 在 35 固件中同样存在，写法一致：
  - 设置 `stallProtectSwitch` 与 `boardConfig.enableStallProtect`
  - `_data[4]` 非 0 时写 EEPROM（CONFIG_COMMIT）

### 1.2 触发条件对比

**结论：无任何差异。**

| 项目 | 35 固件 | 42 固件 |
|------|---------|---------|
| 电流条件 | 电流模式 `current!=0`；其它模式 `current==ratedCurrent` | 同左 |
| 近零速度阈值 | `abs(estVelocity) < MOTOR_ONE_CIRCLE_SUBDIVIDE_STEPS/5` | 同左 |
| 持续时间 | `stalledTime >= 1000*1000`（1 秒，50µs 周期累加） | 同左 |
| 清除方式 | 仅手动 `ClearStallFlag()`（如 KEY2 单击） | 同左 |

35 固件堵转判定代码与 42 一致：

### 1.3 针对 35 小电机的“更敏感”失步逻辑

**结论：无。**

- 35 固件**未**对“轻量化/小扭矩”做单独处理：
  - 未缩短堵转判定时间（仍为 1 秒）
  - 未收紧近零速度阈值（仍为 STEPS/5）
  - 未引入编码器跟随误差阈值或丢步检测
- 因此：35 电机更容易失步是**物理特性**，固件并未用更敏感判据补偿；若需更快感知堵转，只能依赖主控侧启发式或协议扩展（如 42 报告中的 0x26 Get State / 回传 state 字节）。

### 1.4 保护动作

与 42 相同：`isStalled` 后清积分、输出置零、`driver->Sleep()`，状态为 `STATE_STALL`；KEY2 触发 `ClearStallFlag()` 逻辑一致。

## 维度 2：CAN 协议与报警通道的兼容性（CAN Protocol & Telemetry）

### 2.1 指令解析一致性

**结论：35 与 42 支持的 CAN 指令集及解析方式一致。**

| 指令 | 35 | 42 | 说明 |
|------|----|----|------|
| 0x01 使能 | 同：1→MODE_COMMAND_VELOCITY，0→MODE_STOP | 同 | 无差异 |
| 0x05 位置 | 同：float×MOTOR_ONE_CIRCLE_SUBDIVIDE_STEPS，非位置模式时恢复 ratedVelocity=boardConfig.velocityLimit | 同 | 无差异 |
| 0x03/0x04/0x06/0x07 | 同 | 同 | 无差异 |
| 0x11~0x1B（参数与堵转开关） | 同，含 _data[4] 写 EEPROM | 同 | 无差异 |
| 0x21/0x22/0x23/0x24/0x25/0x7d/0x7e/0x7f | 同 | 同 | 无差异 |

主控用同一套“按 cmd 解析 + 按 NodeID 区分电机”即可，无需按 35/42 分支。

### 2.2 回传数据包与错误码

**结论：回传结构一致；两者均无 state/ErrorCode。**

- **0x23 Get Position**  
  - 35：byte[0..3]=GetPosition() 的 float，byte[4]=STATE_FINISH?1:0，与 42 相同。  
  - 无 STATE_STALL / STATE_OVERLOAD / 错误码字段。
- **0x21/0x22**  
  - 同样 byte[4]=STATE_FINISH?1:0，无 state/ErrorCode。
- **0x25 温度**  
  - 结构一致（byte[0..3]=motor_temperature 等）。

因此：**发生堵转、过热、过流时，两种固件都不会在现有回传中带错误码或状态字**；主控无法仅凭 0x23/0x21/0x22 区分“堵转”与“运行中”，需沿用 42 报告中的方案（周期查询 + 启发式，或扩展 0x26/回传 state）。

### 2.3 兼容性小结

- 主控可**统一**解析 35 与 42 的 CAN 请求与回复。  
- 错误/堵转的**可观测性**在两种固件中相同（都缺 state/ErrorCode），若主控已为 42 做了“无法直接读堵转”的应对，可直接复用于 35。

### 3.2 DCE 闭环与误差限幅

**结论：算法与限幅一致。**

35 固件中 DCE 与 42 相同：

- pError = _location - estPosition，限幅 **±3200**（约 1/16 圈）
- vError = (_speed - estVelocity)>>7，限幅 **±4000**
- 输出经 Kp/Ki/Kd 计算后钳在 ±ratedCurrent

```378:401:e:\Dummy-IDE\dummy\firmware\dummy-35motor-fw\Ctrl\Motor\motor.cpp
void Motor::Controller::CalcDceToOutput(int32_t _location, int32_t _speed)
{
    config->dce.pError = _location - estPosition;
    if (config->dce.pError > (3200)) config->dce.pError = (3200);   // limited pError to 1/16r (51200/16)
    if (config->dce.pError < (-3200)) config->dce.pError = (-3200);
    config->dce.vError = (_speed - estVelocity) >> 7;
    if (config->dce.vError > (4000)) config->dce.vError = (4000);   // limited vError
    if (config->dce.vError < (-4000)) config->dce.vError = (-4000);
    // ... 输出计算与 ratedCurrent 钳位
}
```

### 3.3 默认物理极限参数（EEPROM 未配置时的默认值）

| 参数 | 35 (main.cpp 默认) | 42 (main.cpp 默认) |
|------|--------------------|--------------------|
| currentLimit | 1×1000 (1 A) | 1×1000 (1 A) |
| velocityLimit | 30×MOTOR_ONE_CIRCLE_SUBDIVIDE_STEPS | 30×MOTOR_ONE_CIRCLE_SUBDIVIDE_STEPS |
| velocityAcc | 100×MOTOR_ONE_CIRCLE_SUBDIVIDE_STEPS | 100×MOTOR_ONE_CIRCLE_SUBDIVIDE_STEPS |
| dce_kp | **195** | **200** |
| dce_kv / dce_ki / dce_kd | 80 / 300 / 250 | 80 / 300 / 250 |

**结论：**

- 最大电流、最大转速、默认加速度在**默认配置下相同**，固件并未为 35 预设更小极限。  
- **唯一数值差异**为默认 **dce_kp**（35=195，42=200），差异很小，一般可忽略或在上电/标定阶段统一用 0x17 覆盖。  
- 若希望针对 35 电机“更保守”，应在**主控或 EEPROM** 中对 35 所在节点设置更低的 0x12（限流）、0x14（加速度），而不是依赖固件内置差异。

### 3.4 PositionTracker / 梯形规划

35 与 42 的 motion_planner 使用相同的 CONTROL_FREQUENCY/CONTROL_PERIOD、相同的 PositionTracker/VelocityTracker/CurrentTracker 逻辑，0x14 加速度参与规划的方式一致。无“针对 35 的缩小版规划”或不同滤波常数。

## 维度 4：架构师避坑指南与集成建议

### 4.1 能否把 35 当成“缩小版 42”一视同仁控制？

**可以。**

- 协议、状态机、回传格式一致；主控**不需要**因 35 与 42 在 CAN 或状态解析上做 `if (motorID >= 4) { ... }` 类分支。  
- 差异仅体现在**物理**上：35 扭矩更小、更易失步/堵转，固件未在算法或阈值上做专门优化。

### 4.2 是否存在 42 有而 35 无（或逻辑不同）的高级功能？

**不存在。**

- 堵转保护、0x1B、DCE、0x03 电流模式、0x07 带速限位置、0x23 完成位等，35 与 42 均一致。  
- 两者都**没有**“堵转/错误主动 CAN 上报”和“回传中的 state/ErrorCode”，主控侧处理方式可统一。

### 4.3 建议的集成方式

1. **统一驱动逻辑**  
   - 同一套 CAN 指令与回传解析用于全部 6 轴；仅通过 **NodeID** 区分电机，无需按 35/42 分叉。

2. **按轴类型区分“参数”而非“逻辑”**  
   - 对腕部/末端（35 电机）节点：上电或标定时用更保守的 **0x12 限流**、**0x14 加速度**（及必要时 **0x13 限速**），避免 200Hz 大跨度 0x05 时静默失步与堵转率偏高。  
   - 无需在运行中根据 motorID 做特殊分支，除非你主动为 35 轴选用不同目标速度/加速度曲线（业务层决策）。

3. **堵转与错误感知**  
   - 与 42 相同：当前协议下无法从回传直接读堵转/过载；若需可靠感知，需扩展协议（如 0x26 Get State 或回传增加 state 字节），并可在 35/42 固件上同步扩展，保持主控解析仍统一。

4. **默认 DCE**  
   - 若希望 6 轴行为完全一致，可在主控或标定流程中对 35 节点也发 0x17 将 Kp 设为 200（或统一为 195），消除唯一默认参数差异。
